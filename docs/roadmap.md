# План реализации Vulkan для Iris 6100 (Broadwell) под Windows

Состояние на 2026-11-19. Цель — ICD на основе Mesa HasVK поверх WDDM-драйвера
Intel `20.19.15.5171`, без Intel UMD и D3D12. Потолок для этой GPU — Vulkan 1.3:
именно его объявляет upstream HasVK для Gen8 (Vulkan 1.4 HasVK не поддерживает).

Документ разделён на две части: **что уже сделано** (раздел 1, только готовое и
проверенное на железе) и **что осталось** (раздел 2, только несделанное, по
этапам). Порядок этапов в разделе 2 — текущий, его можно менять.

**Приоритет:** сначала снимались риски — то, что может сделать проект
невозможным или потребовать другой архитектуры. Этап 0 выполнен (вывод без
копии — раздел 1.4, ограничения ядра — 1.5, закрытый интерфейс Intel — 1.6).
Этап 1 (отправка команд и синхронизация) и этап 2 (Vulkan 1.3) тоже
выполнены (разделы 1.1–1.2), этап 3 (полнота относительно HasVK) — тоже
(раздел 1.2), этап 5 — тоже. С 2026-11-19 главный — этап 7: сделать Vulkan
быстрее DX11 (проверка на The Talos Principle); полный CTS и сон/пробуждение
стали второстепенными (раздел 2).

**Цель — только эта машина:** Iris 6100 (8086:162b) с драйвером
`20.19.15.5171`. Совместимость с другими GPU (Haswell, другие Broadwell) и
версиями драйвера не нужна; где это упрощает или ускоряет код, ориентируемся
только на эту конфигурацию.

## 1. Сделано

Сейчас ICD объявляет **Vulkan 1.3** и 107 расширений устройства. Выборочный
прогон CTS по 22 группам (~2660 тестов): 1574 Pass, 1 Fail — известное
зависание `tess_factor_barrier_bug` (этап 4) и ResourceError следующего за ним
теста, который отдельно проходит (`native/artifacts/cts-sample.json`; свежий
итог выборки — `build/cts-sample.json`).

### 1.1 Транспорт WDDM
- Устройство, контекст, paging queue, выделения, CPU/GPU-отображения,
  residency, фиксированные GPU-адреса, отправка команд и подтверждённое
  завершение.
- Раскладка адресного пространства HasVK: окно 16 ГиБ, пулы состояния по
  фиксированным адресам.
- Одно выделение — до 1 ГиБ (минимум спецификации 1.1+), бюджет устройства
  3 ГиБ, до 65536 выделений; проверены одно выделение в 1 ГиБ и 768 МиБ живых
  выделений с записью GPU.
- Ожидание страничной очереди (отображение GPU-адреса и резидентность при
  каждом выделении) — по событию от ядра
  (`D3DKMTWaitForSynchronizationObjectFromCpu`), а не опросом со `Sleep(1)`,
  который стоил целый тик таймера (~15,6 мс) дважды на выделение: создание
  и уничтожение устройства — 13 мс вместо 430 мс, 60 циклов swapchain —
  1,0 с вместо 22,5 с, CTS — ~70–100 тестов/с вместо ~5 (процесс `deqp-vk`
  был занят CPU на 8 %, остальное время ждал).
- Сброса кэша CPU вокруг отправок нет: доступ GPU к памяти, отображённой в
  CPU, когерентен с кэшами CPU (общий LLC). Проверено пробой
  `IrisCoherenceProbe` (`native/tests/coherence_probe.cpp`) без единого
  сброса: буферы 64 КиБ (в L2), 1 МиБ и 4 МиБ; запись CPU → чтение GPU,
  GPU пишет поверх строк, которые CPU прочитал или записал («грязных»), —
  0 расхождений в трёх прогонах; регрессия и выборка CTS без сбросов —
  без отличий. Раньше перед каждой отправкой сбрасывались все отображённые
  буферы целиком (у `vkcubepp` — 7 МиБ и 2,3 мс на отправку); теперь CPU на
  600 кадров `vkcubepp` — 0,94 с вместо 3,41 с, в режиме IMMEDIATE ~545
  кадров/с. `HASVK_WDDM_CPU_FLUSH=1` возвращает сбросы (диагностика).

- Все командные буферы одного `vkQueueSubmit` и запись счётчика завершения
  идут одной отправкой в ядро: хвост каждого буфера при отправке становится
  переходом на следующий. Отдельные отправки — только у ожиданий событий и
  повторно отправленного (simultaneous-use) буфера. Восемь буферов в одной
  отправке: 0,1–0,25 мс на буфер (было 0,52 мс). Проверка порядка — тест
  `submitOrder` в `IrisGraphicsProbe`.
- Неблокирующая очередь: поток очереди не ждёт GPU после отправки;
  отдельный поток завершения ждёт её, проверяет маркеры, защитные области и
  счётчик и сигналит все синхронизации отправки разом. Entry-BO — кольцо из
  64 слотов; командный буфер переиспользуется только после проверки его
  прошлого выполнения. Отправки подряд: 0,77 мс против 1,24–1,30 мс с
  ожиданием каждой (`HASVK_WDDM_SYNC_SUBMIT=1` включает прежний режим).
  Основная цена отправки — планирование в драйвере ядра, поэтому объединение
  буферов даёт больше, чем асинхронность.
- Вывод окна не ждёт GPU (см. 1.4: копия кадра идёт в WSI-отправке через
  очередь). До этого, при отдельной отправке копии, `vkcube` на 1000 кадров
  тратил 8,3 с против 8,7 с с ожиданием каждого кадра и 12,1–12,5 с до
  неблокирующей очереди.
  Отправки, разрезанные ожиданием события, остаются блокирующими: CPU всё
  равно должен увидеть событие перед продолжением.

- MSAA 2x/4x/8x, `vkCmdResolveImage`, blit с линейным фильтром проверены

  атомиков в одну ячейку при измеренных 287 млн/с на этой GPU (≥2,1 с).
  Записан в `docs/cts-expected-failures.md`.
- Командные буферы: цепочка BO без ограничения размера, secondary command
  buffers (копируются в primary).
- Events: отдельный BO; `MI_SEMAPHORE_WAIT` в WDDM-контексте не работает,
  поэтому `vkCmdWaitEvents` вне рендеринга разрезает батч, и очередь ждёт
  события на CPU. Внутри прохода рендеринга ждать нечего: события там могут
  быть установлены только раньше по порядку отправки (установка с хоста после
  отправки запрещена, `VUID-vkCmdWaitEvents-pEvents-01163`), а очередь
  выполняет всё строго по порядку, поэтому остаётся только барьер памяти.
  Проверено режимом 8 теста отрисовки: инстансы записываются передачами,
  событие ставится после них, отрисовка ждёт его внутри прохода — все пиксели
  совпадают.
- Барьеры — штатные HasVK: сбросы и инвалидации кэшей по маскам стадий и
  доступа, а не полный сброс на каждый барьер. CTS `memory.pipeline_barrier`,
  барьеры `synchronization`/`synchronization2`, `synchronization.basic`:
  580 Pass, 0 Fail.
- Потокобезопасность: параллельная запись командных буферов из нескольких
  потоков, выделение памяти, буферов и событий, отправка под мьютексом
  приложения (тест `threads` в `IrisGraphicsProbe`: 4 потока × 40 отправок).
- Два типа памяти, как у upstream HasVK для GPU с общим LLC: тип 0 —
  `DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT | HOST_CACHED` (кэшируемое
  отображение; GPU когерентен с кэшами CPU, см. 1.1), тип 1 — только
  `DEVICE_LOCAL`: выделяется без отображения в CPU (нет `Lock2`, не занимает
  адресное пространство процесса, никогда не сбрасывается). Тест
  `deviceLocalMemory`: `vkMapMemory` отказывает, GPU пишет и копирует.
- Редкий сбой compute 16.11 (`build/failures`, «mismatch at word 16») на
  нынешнем коде не воспроизводится: 1200 итераций того же случая (1000 из
  них без сброса кэша CPU) и 5 прогонов SPIR-V-теста подряд — без сбоев
  (`native/artifacts/compute-rootcause.json`). Сброс кэша на этот случай не
  влияет, то есть тогда помог не он, а вероятнее ожидание настоящего
  завершения GPU, добавленное тем же изменением; исходный код до сбоя в git
  не сохранился, поэтому причина не доказана.
- Потеря устройства (`tools/test-device-lost.ps1`): при настоящем зависании
  GPU (бесконечный compute-шейдер, Windows сбрасывает GPU по TDR) ожидание
  забора возвращает `VK_ERROR_DEVICE_LOST` через ~4,5 с, дальнейшие вызовы
  сразу сообщают о потере и не блокируются, устройство уничтожается, новое
  `VkDevice` в том же процессе работает.
- Адреса буферов (`VK_KHR_buffer_device_address`, A64-доступ); CTS
  `buffer_device_address`, `ssbo.phys`, `physical_pointers`: 629 Pass, 0 Fail.

### 1.3 Шейдеры, compute, графика
- SPIR-V → NIR → ELK → Gen8 для всех стадий: VS, TCS, TES, GS, FS, CS.
- Compute: 3D-группы до 1024 потоков, shared memory, indirect dispatch.
- Графика: vertex input, все формы draw (indexed, instanced, indirect,
  indirect count, multi draw), blending, stencil, depth, MSAA 4x с resolve,
  dynamic state, dynamic rendering, renderpass2, imageless framebuffer.
- 47 форматов (цвет, depth, stencil) и 1D/2D/3D/cube-изображения с
  mip-уровнями и слоями; команды копирования, blit и clear.
- Queries: occlusion, pipeline statistics, timestamp.
- Исправленные ошибки порта, найденные CTS: выравнивание mip-уровней (HALIGN),
  относительная адресация push-буфера 0, события, texel-буферы.

### 1.4 Вывод на экран
- `VK_KHR_surface`, `VK_KHR_win32_surface`, `VK_KHR_get_surface_capabilities2`,
  `VK_KHR_surface_protected_capabilities`, `VK_KHR_swapchain`,
  `VK_KHR_swapchain_mutable_format`.
- Форматы поверхности B8G8R8A8 и R8G8B8A8, UNORM и SRGB: B8G8R8A8 копируется
  в поверхность окна как есть, R8G8B8A8 — blit с перестановкой каналов;
  поверхность окна берёт SRGB-вид для SRGB-цепочки, поэтому закодированные
  байты не перекодируются. Запасной путь GDI переставляет каналы на CPU.
- Режимы FIFO, MAILBOX, IMMEDIATE. FIFO после вывода спит до следующего
  vblank по времени композиции DWM (`DwmGetCompositionTimingInfo`,
  высокоточный таймер): 16,7 мс на кадр при 60 Гц — и при включённом, и при
  выключенном экране (`DwmFlush`, проверенный сначала, при выключенном экране
  ждал ~270 мс на кадр, и CTS почти вставал). MAILBOX и IMMEDIATE не ждут —
  2,7–3,4 мс на кадр (раньше единственный FIFO фактически работал как MAILBOX).
- Возможности поверхности по `VK_KHR_win32_surface`: `minImageExtent` =
  `maxImageExtent` = `currentExtent` = клиентская область (upstream объявлял
  1…16384, и CTS создавал цепочку 31×31 в окне 400×300).
- Нехватка памяти при создании swapchain (CTS `simulate_oom`): неудачная
  загрузка шейдера BLORP помечает командный буфер ошибкой
  `VK_ERROR_OUT_OF_HOST_MEMORY` вместо assert в upstream BLORP.
- Размер окна: если клиентская область не совпадает со swapchain, вывод
  возвращает `VK_SUBOPTIMAL_KHR`, а получение кадра — `VK_ERROR_OUT_OF_DATE_KHR`
  (как у других драйверов Windows); пересоздание с `oldSwapchain` работает.
  Свёрнутое окно (0×0) несовпадением не считается: цепочка продолжает
  работать через GDI, а создание цепочки нулевого размера возвращает
  `OUT_OF_DATE` вместо падения (vkcube пересоздавал так и падал на assert).
- Попиксельная проверка кадра (`tools/test-wsi.ps1`, `IrisWsiProbe`, в
  `test-all`): своё окно, которое закрывается само; все четыре формата —
  каждый пиксель клиентской области (снимок `PrintWindow`) совпадает с
  ожидаемым цветом, также после пересоздания цепочки нового размера; все
  кадры прошли перенаправленным выводом, без GDI. При выключенном экране или
  заблокированной сессии (`GUID_CONSOLE_DISPLAY_STATE`, `OpenInputDesktop`)
  DWM не компонует: тот же тест проверяет запасной путь GDI (все форматы тоже
  совпадают попиксельно); темп FIFO одинаков в обоих случаях.
- Копия кадра в отправке WSI проверена и при выключенном экране (отказ ядра
  → повтор без токена → GDI), и при включённом: все кадры теста прошли
  перенаправленным выводом, 0 через GDI.
- Нестандартная геометрия окон (`IrisWsiProbe`): окно без рамки (`WS_POPUP`)
  — перенаправленный вывод, каждый пиксель верен; дочернее окно — через GDI
  в его собственный DC (DWM перенаправляет только окна верхнего уровня, токен
  для дочернего HWND не проверялся), каждый пиксель верен по снимку родителя.
- **Вывод без копии через CPU и без D3D** (`anv_wddm_present.c`): GPU копирует
  кадр (BLORP) в разделяемую поверхность окна, отправка идёт с флагом
  `PresentRedirected` и токеном `(0x80000000 | HWND) << 32 | дескриптор`,
  DWM показывает поверхность. Так выводит кадры OpenGL-драйвер Intel того же
  пакета (снято трассировкой, `tools/trace-gl-present.ps1`). Поверхность
  создаёт наш транспорт по снятому описателю (1096 байт Intel + 104 байта
  данных рантайма): B8G8R8A8, Y-тайлинг, шаг `align(ширина × 4, 128)`, высота
  кратна 32, без отображения в CPU; размер — всё окно с рамкой, кадр
  копируется со смещением клиентской области. Условие — приватные данные
  контекста как у OpenGL-драйвера (без них DWM показывает чёрное); выборка CTS
  с ними — 0 Fail. D3D, Intel UMD и ICD в процессе не загружаются.
- Копия кадра в поверхность окна записывается при `vkQueuePresentKHR` и
  идёт командным буфером в собственной отправке WSI (той, что ждёт семафоры
  приложения), за работой приложения в той же упорядоченной очереди; эта
  отправка в ядро и есть вывод (токен на командном буфере). Нет ожидания
  кадра на CPU и нет отдельной отправки копии: на кадр — одна отправка вывода
  вместо пустой отправки WSI, ожидания её забора на CPU и отдельной копии.
  Командный буфер копии — свой для каждого индекса изображения (WSI ждёт
  прежний вывод того же индекса); при смене размера окна очередь
  дожидается простоя перед заменой поверхности.
- Откат на прежний путь (копия в CPU-буфер + GDI): если ядро отказывает в
  выводе (`PRESENT_OCCLUDED` при спящем экране), поток очереди повторяет ту же
  отправку без токена, а следующий кадр идёт через GDI (с ожиданием его копии
  на CPU); затем снова пробуется вывод. `HASVK_WDDM_PRESENT=gdi` включает GDI
  принудительно.
- Неизменённый `vkcube`: 40 с с resize и minimize под validation layers —
  3063 кадра через поверхность окна, 0 через GDI, 0 ошибок; окна от 200×150
  до 1280×720, в том числе частично за краем экрана (GDI там рисовал пусто).
  Скорость пока равна GDI-пути: узкое место — синхронная отправка (этап 1).
- Проверки: `tools/test-present-redirect.ps1` (своя поверхность, цвета и
  раскладка по пикселям экрана), `tools/capture-vkcube.ps1 -Present redirect|gdi`.

## 2. Осталось

**Приоритет с 2026-11-19 (решение пользователя):** главный вопрос — как
сделать Vulkan быстрее DX11. Основной испытательный стенд — The Talos
Principle: это работающая игра с обоими API, она ближе к реальной задаче,
чем CTS. Полный прогон CTS и проверка сна/пробуждения — второстепенные.

### Этап 7 (главный). Vulkan быстрее DX11 в The Talos Principle

**Цель и мера.** Средний FPS встроенного бенчмарка (Demo, 30 с, 640×480,
одинаковые авто-настройки) через `tools/run-talos.ps1`, оба API подряд в
одном состоянии машины; вторично — 1 % худших кадров. Сейчас: DX11 80–86 FPS,
Vulkan 35,5 FPS (1 % худших — 36 против ~20).

**Где разрыв** (подробно — `docs/optimizations-vs-dx11.md`, раздел 1):
~17 мс GPU на кадр у Vulkan против ~9 у DX11. Вне теней Vulkan отстаёт на
10–20 % (≈1 мс). Почти весь разрыв (~7 мс) — две карты теней 1536²: при
том же числе вершин (161 тыс. против 181 тыс. вызовов VS) путь Vulkan игры
выполняет фрагментный шейдер на 3,7 млн пикселей за проход, а путь DX11 — на
7 тыс. На одинаковой работе драйвер уже наравне с драйвером Intel
(микротесты VS, выборки, заливки глубины и альфа-теста), значит, только
ускорением драйвера разрыв не закрыть: оценка всех пунктов плана —
~45–55 FPS.

**Отправная точка — HasVK** (указание пользователя 2026-11-19): теперь, когда
Vulkan работает, код можно оптимизировать относительно upstream, не
ограничиваясь им, — в том числе там, где upstream выбирает иначе.

**Шаги.**
1. **Понять, что рисует путь DX11 в тенях** — от ответа зависит, возможно
   ли обогнать DX11. *Сделано частично (2026-11-19):* дампы карт теней
   (`D3D11_DUMP_DIR` в прокси, `HASVK_WDDM_DUMP_DIR` в профилировщике
   драйвера, `build/talos/shadow/*.png`) показывают в обоих путях одинаково
   детальные кроны деревьев; при этом за 880 проходов теней DX11 ни в одном
   нет больше 100 тыс. вызовов PS (максимум 56 тыс.), а у Vulkan — 3,7 млн в
   каждом. То есть путь DX11 рисует листву в тенях практически без
   пиксельного шейдера и каждый кадр, а путь Vulkan — с шейдером альфа-теста.
   Гипотеза: детали крон дают сами треугольники, и альфа-тест пути Vulkan
   почти не меняет карту. Подтвердить можно только сравнением **одного и
   того же кадра** (дампы сняты в разные моменты: время «35 с» у API
   разное).
   - Снять обе карты теней одного кадра и сравнить: прокси `d3d11.dll`
     копирует буфер глубины 1536² в staging и пишет файл; на стороне Vulkan
     то же делает профилировщик драйвера. Видны ли в карте DX11 «дырки»
     альфа-теста листвы, то есть рисуется ли листва в тенях DX11 вообще и с
     альфа-тестом ли.
   - Разбить проход теней DX11 по смене шейдеров (перехват `PSSetShader`/
     `VSSetShader` в прокси, статистика конвейера на каждый участок): какие
     объекты идут без пиксельного шейдера.
   - Перебрать настройки игры, влияющие на тени и листву (`shb_*`,
     `crm_bCastShadows`, `vlk_*`), — нет ли такой, при которой путь Vulkan
     рисует тени как путь DX11.
2. **По итогам шага 1:**
   - если путь DX11 рисует то же самое, но дешевле, — найти чем (порядок,
     ранний тест глубины, другие шейдеры) и повторить в драйвере;
   - если путь DX11 рисует меньше (например, листву в тенях без альфа-теста) —
     честное сравнение требует той же работы от пути Vulkan: настройкой игры,
     если она есть; иначе профиль приложения в драйвере, который меняет то,
     что просит игра, — это решение пользователя, без него не делается.
3. **Стоимость теней в драйвере** (не меняя изображения): переключения обхода
   PMA, 88 за кадр (п. 2.5 плана); SIMD16 для тяжёлых FS (2.2); код ELK для
   цепочки `sqrt`/`inv`/`sin`/`cos` в цикле VS листвы; быстрая очистка HiZ уже
   есть как опция (`HASVK_WDDM_NO_HIZ_SAMPLING`, 2.10).
4. **Остальной кадр** (~1 мс): остановки VF-кэша (2.4), сбросы в барьерах
   (2.6), фиксированный путь вершин — 89 % от D3D11 (2.9), сэмплер и АЛУ —
   73–85 % (2.7), мелкие проходы пост-обработки (1,8 против ~1 мс).
5. **CPU и подача кадров** — когда GPU-разрыв закроется: главный поток игры
   ~56 % ядра; у Vulkan здесь преимущество (многопоточная запись), его надо
   не потерять в отправке и ожиданиях WDDM (`rip_sampler`). 1 % худших кадров —
   кэш шейдеров (2.8).

**Метод.** Каждое изменение — A/B в Talos (по два прогона подряд на
вариант, одно тепловое состояние), разбивка проходов в обоих API
(`HASVK_WDDM_PROFILE_PASSES`, `run-talos.ps1 -D3D11Proxy`), `test-all`;
изменения конвейера и глубины дополнительно страхуются выборками CTS по
затронутым группам (полный прогон — второстепенен).

### Второстепенное (решение пользователя 2026-11-19)
- Полный прогон CTS (этап 4 ниже) — после главного этапа или по команде

### Этап 4 (второстепенный). Полный прогон CTS
1. Полный mustpass для объявленной версии — последний шаг: 2,89 млн тестов
   в списках `vk-default`. Параллельный запуск готов (`run-cts.ps1 -Jobs N`,
   также в `run-cts-groups.ps1` и `run-cts-sample.ps1`): тесты раздаются
   по N процессам `deqp-vk` с отдельными кэшами шейдеров, всё непрошедшее
   перепрогоняется в одном процессе, итог отдельно перечисляет
   `flakyUnderParallel`. На 2934 тестах `pipeline.monolithic`: 40,8 с в один
   процесс, 30,8 с в 2, 27,8 с в 3 (упор в два ядра CPU), результаты
   совпадают. После исправления ожидания страничной очереди (раздел 1.1) CTS
   идёт ~70–100 тестов/с вместо ~5: полный прогон — порядка 8–10 часов.
2. Список ожидаемых отказов с причинами — начат
   (`docs/cts-expected-failures.md`), пополняется по итогам полного прогона.

   `VK_ERROR_OUT_OF_DEVICE_MEMORY`, 511,9 из 512 МиБ; с полной кучей
   записанная заранее работа и новый буфер на 20 000 команд выполняются
   верно; после освобождения помещается ровно тот же объём. Куча сужается
   `HASVK_WDDM_HEAP_MB` (64 МиБ … 3 ГиБ), чтобы не исчерпывать память
   машины; пути кода те же. Найдено и исправлено: внутренняя память
   драйвера (пулы состояний, блоки команд) считалась в куче приложения, и
   при полной куче рост пула в upstream повторялся бесконечно —
   приложение зависало внутри `vkCmd*`. Теперь у внутренней памяти свой
   предел (1 ГиБ), рост пула повторяется 64 раза через 1 мс, затем процесс
   завершается с сообщением о причине; структуры `anv_bo` берутся из
   `malloc`, как в upstream `bo_cache`, а не из обратных вызовов
   приложения (иначе `simulate_oom` падал). CTS: `simulate_oom` — 11 Pass,
   `api.device_init` (каждый 2-й) — 107 Pass (раньше 1 Crash),
   `memory.allocation`, `object_management`, `api.buffer` — 0 Fail.
   Минута непрерывного рендеринга `vkcubepp` (3600 кадров, все
   через окно): частная память 16,2–16,3 МБ, дескрипторы 214–215 — без
   роста (`native/artifacts/stability-vkcubepp.json`). Тогда CPU был занят
   на треть ядра; причиной оказался сброс кэша перед каждой отправкой, он
   убран (раздел 1.1). Утечки проверены (`tools/test-leaks.ps1`, `IrisLeakProbe`):
   150 жизненных циклов устройства (память, буфер, изображение, отправка) и
   60 циклов swapchain с выводом — частная память, дескрипторы ОС и
   GDI-объекты не растут. Найдена и исправлена утечка upstream WSI: `GetDC`
   на каждое изображение и `DeleteDC` вместо `ReleaseDC` — 2 GDI-объекта на
   swapchain.
4. Релизный пакет и инструкция готовы: `tools/make-release.ps1` собирает
   `build/release/HasVK-WDDM-<дата>-<коммит>.zip` (ICD, манифест,
   `IrisIcdProbe` с шейдерами, `install-icd.ps1`, инструкция
   `docs/install.md`, список ожидаемых отказов, SHA-256). Проверено: проба
   из распакованного пакета проходит, `install-icd.ps1 -WhatIf` из него
   показывает верные шаги. Поддерживаемая конфигурация — одна (Iris 6100,
   драйвер `20.19.15.5171`). Остаётся: собрать пакет после финальных
   проверок этапов 4–6.

## 3. Риски

- **Закрытый интерфейс Intel** — описан и ограничен одной версией драйвера
  (раздел 1.6): на другой ICD безопасно не включается. Остаётся неизвестным,
  насколько значения стабильны между версиями, — проверить нельзя без другой
  версии драйвера; перенос — по `docs/intel-interface.md`.
- **Вывод без CPU-копии** — снят: вывод через перенаправленную отправку
  работает в ICD без D3D (раздел 1.4). Остаточный риск — описатель
  поверхности снят с одного драйвера, как и остальные описатели.
- **Ограничения ядра** — проверены (раздел 1.5): кроме `MI_SEMAPHORE_WAIT`
  запретов нет. Остаточный риск — команды, которых HasVK пока не использует
  в нашей конфигурации (perf-запросы с настройкой OA-регистров).
- **Объём CTS.** Полный прогон — миллионы тестов; нужны параллельность и
  хранение результатов между сессиями.
