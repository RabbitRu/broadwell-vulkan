# Состояние и план

Состояние на 2026-11-21. ICD на основе Mesa HasVK 26.2.7 поверх WDDM-драйвера
ядра Intel `20.19.15.5171`, только для Iris 6100 (`8086:162b`) и этой версии
драйвера (совместимость с другими GPU и версиями не нужна). Без Intel UMD и
D3D. **Цель пользователя — Dota 2 под Vulkan быстрее, чем под DX11.**

Какой документ для чего:
- этот — что сделано (только то, что важно помнить), что осталось, риски;
- [optimizations-vs-dx11.md](optimizations-vs-dx11.md) — производительность:
  итоги по Talos и Dota, **реестр проверенных гипотез** (смотреть перед любым
  новым опытом), как мерить, подводные камни;
- [cts-expected-failures.md](cts-expected-failures.md) — отказы CTS и
  исправленные ошибки, найденные CTS;
- [intel-interface.md](intel-interface.md) — закрытый интерфейс Intel;
- [install.md](install.md) — установка и переменные окружения (идёт в пакет).

Правила работы (решения пользователя): только универсальные исправления
драйвера, без профилей под игры; тесты и замеры — без подтверждения;
системные настройки, установка драйвера и скачивание — только с согласия;
опыты, которые могут повесить GPU, — только с согласия (раздел 3).

## 1. Сделано

### 1.1 Транспорт WDDM (`native/src`, `mesa/anv_wddm_*.c`)
- Устройство, контекст, paging queue, выделения с фиксированными GPU-адресами
  (окно 16 ГиБ, пулы состояния по фиксированным адресам), отправка и
  подтверждённое завершение. Куча приложения 3 ГиБ (`HASVK_WDDM_HEAP_MB`),
  одно выделение до 1 ГиБ, до 65 536 выделений; память самого драйвера —
  отдельный предел 1 ГиБ (`ANV_WDDM_INTERNAL_BYTES`).
- Ожидание очереди подкачки — по событию ядра, а не опросом со `Sleep(1)`
  (тот стоил тик таймера 15,6 мс). Выделение памяти не ждёт подкачку на CPU:
  ближайшая отправка ждёт её на GPU, как D3D-рантаймы. Вызовы ядра при
  выделении — без общих мьютексов (иначе главный поток игры стоял до 40 мс).
- Сброса кэша CPU вокруг отправок нет: GPU когерентен с кэшами CPU (общий LLC),
  проверено `IrisCoherenceProbe`. Отображение памяти в CPU кэшируемое и по
  скорости как у D3D11 (`cpu_map_probe`: запись/чтение ~15/14 ГБ/с, как у
  обычной памяти процесса).
- Все буферы одного `vkQueueSubmit` идут одной отправкой в ядро (хвост буфера
  становится переходом на следующий). Очередь неблокирующая: поток очереди
  отправляет, поток завершения ждёт GPU, проверяет маркеры и защитные области
  и сигналит синхронизации. Цена отправки — в основном планирование в ядре.
- `MI_SEMAPHORE_WAIT` в нашем контексте не завершается: `vkCmdWaitEvents` вне
  прохода рендеринга режет батч, очередь ждёт события на CPU. Остальные 46
  проверок регистров и MI-команд HasVK проходят (`test-kernel-limits.ps1`).
- Командный буфер: цепочка BO 8 КиБ, затем по 64 КиБ; первый блок таблиц
  привязок записи 4 КиБ; запасные BO команд общие на устройство (до 512).
  Иначе тысячи мелких буферов Dota съедали память драйвера (1.10).

### 1.2 Возможности и ошибки порта
- Vulkan 1.3, 108 расширений устройства; таблицы HasVK
  (`anv_wddm_capabilities.c`), расширения — только из проверенного списка
  (`verified_device_extensions` в `anv_wddm_device.c`;
  `HASVK_WDDM_EXTRA_EXTENSIONS` включает остальные для разбора). Выключены
  только Linux-расширения (dma-buf, DRM, fd, `pci_bus_info`,
  `queue_family_foreign`). Нет sparse, внешней памяти, transfer-очереди;
  `descriptorIndexing` (variable count, update-after-bind, кроме inline
  uniform) не объявлен, как и в upstream для Gen8.
- HiZ для глубины возвращён (в upstream HasVK поверхность HiZ вычислялась и
  выбрасывалась): без него проход глубины в 10 раз медленнее драйвера Intel.
  MCS включён. CCS_D выключен: ускоряет только быстрые очистки цвета, а resolve
  в мип-уровень 3 с ним неверен. `HASVK_WDDM_NO_AUX=1` выключает всё.
- Только Gen8: из сборки убраны другие поколения (ветка `all-gens` хранит
  прежний код), сравнения поколения свёрнуты в константы (`gen8_fold()`).
- Классы ошибок порта, на которые уже наткнулись (искать похожее в первую
  очередь):
  - то, что в Linux заполняет Linux-часть Mesa: `max_scratch_ids` (буфер сброса
    регистров — зависания GPU), driconf не читается (`lower_depth_range_rate`),
    `robust_buffer_access` не выставлялся;
  - ABI Microsoft: битовое поле с типом перечисления знаковое
    (`DepthUnchanged` → −4, зависание GPU). Новые каталоги сборки проверять
    `-Wbitfield-enum-conversion`; аудит всех файлов сделан 2026-11-20;
  - ошибка upstream: `continue` в сериализованном NIR (2 бита) становился
    `return` — поле расширено, тест `IrisNirSerializeTest`;
  - `u_memstream` оставлял временный файл на каждую компиляцию (65 535 файлов
    в `%TEMP%`);
  - сгенерированные файлы `anv_wddm_graphics_*.c`, `anv_wddm_command_*.c`
    строятся из **исходных** файлов upstream (`graphics_sources.py`,
    `compute_sources.py`): правка upstream-файла через `apply-compiler-port.py`
    в них не попадает. В `apply-compiler-port.py` у файла — один вызов `edit()`.
- Набор без буфера дескрипторов (в раскладке нет буферов, storage-изображений
  и inline uniform), привязанный туда, где шейдер читает буфер дескрипторов:
  upstream разыменовал бы NULL, у нас батч отвергался и Dota получала
  DEVICE_LOST (3 из 9 прогонов). Теперь ставится нулевая поверхность (1.10).

### 1.3 Вывод на экран (`anv_wddm_present.c`)
- Как у OpenGL-драйвера Intel: GPU копирует кадр в разделяемую поверхность
  окна, отправка с флагом `PresentRedirected` и токеном, DWM показывает.
  Копия записывается при `vkQueuePresentKHR` и идёт в отправке WSI той же
  очереди: ожидания кадра на CPU нет. Описатели — `intel-interface.md`.
- Если ядро отказывает в выводе (экран спит), отправка повторяется без токена,
  кадр идёт через GDI; дочерние окна — всегда GDI. FIFO спит до vblank по
  `DwmGetCompositionTimingInfo` (`DwmFlush` при выключенном экране ждал
  ~270 мс). Изображения выдаются по кругу (throttle как у flip-модели DXGI).
- Без копии: изображения swapchain формата B8G8R8A8 сами выделяются как
  поверхности окна (`anv_AllocateMemory`), и вывод в окно без рамки ровно их
  размера отдаёт DWM само изображение — пустой буфер команд с токеном этого
  изображения (у каждого свой). Dota +4–6 % (G7). DWM читает поверхность
  только как B8G8R8A8, поэтому форматы R8G8B8A8 для окна не сообщаются (G12);
  созданный с ними swapchain, окна с рамкой, дочерние окна и несовпадение
  размеров идут через копию. `HASVK_WDDM_PRESENT_DIRECT=0` — всегда копия.
- Цена: вызов ядра с выводом ~1 мс CPU потока очереди (в Dota — до 3 мс по
  времени); копия 2560×1600 — ~2,4 мс GPU. Путь DXGI (копию строит драйвер
  ядра) — E7, не делался.

### 1.5 Пригодность для приложений
- `tools/install-icd.ps1` (от администратора) регистрирует копию в
  `%ProgramFiles%\HasVK-WDDM`. Установлен пакет `HasVK-WDDM-20261122-6468d32`
  (2026-11-22: релиз без переключателей для замеров и отладочного вывода;
  SHA-256 файлов совпадают с пакетом, `IrisIcdProbe` через системный загрузчик
  проходит, Dota 2 через установленный ICD — 24,8 FPS).
  Переустановка — с согласия пользователя.
- Пакет — `tools/make-release.ps1`. Прошли: `vulkaninfo`, `vkcube`,
  `vkcubepp`, Talos, Dota 2. Проверки устойчивости (10 мин vkcubepp без роста
  памяти и дескрипторов), нехватки памяти, утечек — в `test-all` и
  `test-stability.ps1`.
- Кэш шейдеров: `%LOCALAPPDATA%\HasVK-WDDM\internal-cache.bin` (BLORP) и
  `default-cache.bin` (все конвейеры, и с `VkPipelineCache` приложения, до
  256 МиБ). UUID кэша меняется с каждой сборкой и с `INTEL_DEBUG`: первый
  запуск после пересборки холодный.

### 1.6 Производительность в The Talos Principle (этап закрыт)
Vulkan 70–83 FPS против 79–87 у DX11 (было 27,8). Разрыв задаёт путь Vulkan
самой игры (перестроение карт теней каждый кадр); без построения теней Vulkan
114–124 против 114–117. Драйвер на главном потоке дешевле драйвера Intel
(2,35 против 3,37 мс на кадр). Что сделано и что отклонено — реестр в
`optimizations-vs-dx11.md`.

### 1.7 Dota 2 (этап 8, текущий)
- Замер: `tools/run-dota.ps1` — запись матча 9093360730 как timedemo, тики
  30000–33000 (2999 кадров), всегда `-insecure`; настройки игрока сохраняются
  и возвращаются. `-Sample` / `-RipModule` — потоки и стеки в окне замера.
  Настройки игрока: окно 2560×1600 без рамки, масштаб отрисовки 0,4, всё на
  минимуме.
- Исправлено: нехватка собственной памяти драйвера на ~4400 мелких буферах
  команд (1.1); компиляция всех конвейеров при каждом запуске (игра не
  сохраняет свой `VkPipelineCache` — теперь его подхватывает
  `default-cache.bin`, 1.5); DEVICE_LOST из-за набора без буфера дескрипторов
  (1.2; сообщение в stderr: «descriptor set N is bound without a descriptor
  buffer»).
- Итог: Vulkan 23,2–24,7 FPS, DX11 26,0–26,9 (разброс между сериями — от
  прогрева; сравнивать только чередованием). Разбор — `optimizations-vs-dx11.md`,
  раздел 0: кадр упирается в CPU кода самой игры, время GPU на кадр под
  обоими API одинаковое (~29 мс), драйвер на критическом пути почти не стоит.

## 2. Осталось

### Этап 8 (главный). Dota 2 под Vulkan
1. Вывод без копии (G7) сделан: Vulkan 25,5–25,7 FPS против 25,4–26,1 у
   DX11. Чтобы обогнать DX11, остаётся код игры (`rendersystemvulkan`,
   particles, рабочий поток игры дольше). Открытые идеи — реестр, раздел 1
   (группа G): загрузка рабочего потока игры (G6, G8).
2. Память: игра под Vulkan берёт до 2,4 ГиБ при 7,9 ГиБ ОЗУ; проверить бюджет
   текстур против нашей кучи 3 ГиБ и паузы подкачки.
3. Обычная игра с ботами (не timedemo), полноэкранный режим, сравнение
   картинки DX11 и Vulkan.

Ограничения: VAC — сэмплер, прокси и самодельный драйвер только с
`-insecure`; что античит скажет о драйвере в сетевой игре, неизвестно (решение
пользователя). Под Linux Dota идёт через Vulkan на этом поколении Intel
(HasVK), так что набора возможностей HasVK рендеру Source 2 хватает.

## 3. Риски и меры безопасности

- **Зависание GPU может уронить систему.** Windows сбрасывает зависший
  видеодвижок сама (отчёт LiveKernelEvent 141, приложение получает
  `VK_ERROR_DEVICE_LOST`), но драйвер ядра Intel после такого сброса дважды
  закончил критической ошибкой: 0x119 (2026-11-20 01:06, первый прогон Talos с
  правилом обхода PMA C1) и 0xD1 (13:38, тест CTS со сбросом регистров). Около
  50 зависаний за всё время. Обе найденные причины (буфер сброса регистров,
  `DepthUnchanged`) исправлены. Число отчётов 141 — папки `Kernel_141_*` в
  `C:\ProgramData\Microsoft\Windows\WER\ReportQueue` и `ReportArchive`.
- Меры: состояние GPU сверх того, что требует PRM, не менять без основания в
  PRM; опыты, вешающие GPU, — только с согласия; после сбоя — сначала
  несколько `test-all` (после перезагрузки родной пробник транспорта дважды
  зависал без участия ICD, после паузы проходил), потом нагрузка; после
  оборванного прогона проверить настройки игры (скрипты возвращают их в
  `finally`, но не при перезагрузке). Неверный адрес в команде GPU (например,
  NULL BO) — тоже путь к зависанию: драйвер отвергает такие батчи, а не
  отправляет.
- Приём для разбора зависаний: перед каждой отрисовкой и операцией BLORP —
  `PIPE_CONTROL` с остановкой и записью номера шага в память командного буфера;
  после потери устройства последний номер показывает шаг (временный код через
  `graphics_sources.py`, в сборке его нет).
- Закрытый интерфейс Intel снят с одной версии драйвера; на другой ICD не
  включается (`intel-interface.md`).
- «Быстрее DX11» зависит от игры: в Talos недостижимо универсальными
  правками; у этого процессора (2 ядра, 28 Вт) общий бюджет питания CPU и GPU.
