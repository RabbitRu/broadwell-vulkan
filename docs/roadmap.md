# План реализации Vulkan для Iris 6100 (Broadwell) под Windows

Состояние на 2026-11-20. Цель — ICD на основе Mesa HasVK поверх WDDM-драйвера
Intel `20.19.15.5171`, без Intel UMD и D3D12. Объявлен Vulkan 1.3: именно его
объявляет upstream HasVK для Gen8 (что нужно для 1.4 — раздел 2, «Возможный
этап»). Конечная цель пользователя — Dota 2 под Vulkan быстрее, чем под DX11.

Документ разделён на две части: **что уже сделано** (раздел 1, только готовое и
проверенное на железе) и **что осталось** (раздел 2, только несделанное, по
этапам). Порядок этапов в разделе 2 — текущий, его можно менять.

**Приоритет:** сначала снимались риски — то, что может сделать проект
невозможным или потребовать другой архитектуры. Выполнены этап 0 (вывод без
копии — раздел 1.4, ограничения ядра — 1.5, закрытый интерфейс Intel — 1.6),
этап 1 (отправка команд и синхронизация, 1.1), этап 2 (Vulkan 1.3, 1.2),
этап 3 (полнота относительно HasVK, 1.2) и этап 5 (вывод на экран, 1.4).
Этап 7 (Vulkan быстрее DX11 в The Talos Principle) измерен до конца: 70–83 FPS
против 79–87 у DX11, и универсальными исправлениями драйвера разрыв не
закрывается (раздел 1.8). Полный прогон CTS выполнен (этап 4, раздел 1.10),
релизный пакет собран (1.9). Главный теперь этап 8 — Dota 2 (раздел 2).

**Цель — только эта машина:** Iris 6100 (8086:162b) с драйвером
`20.19.15.5171`. Совместимость с другими GPU (Haswell, другие Broadwell) и
версиями драйвера не нужна; где это упрощает или ускоряет код, ориентируемся
только на эту конфигурацию.

## 1. Сделано

Сейчас ICD объявляет **Vulkan 1.3** и 107 расширений устройства. Полный
mustpass CTS 1.4.5.5 пройден 2026-11-20 (раздел 1.10): 2 849 001 тест, из 90
непрошедших после исправлений проходят 87; остаются ожидаемый отказ и два
теста, вешающие видеодвижок. Все известные отказы —
`docs/cts-expected-failures.md`.

### 1.1 Транспорт WDDM
- Устройство, контекст, paging queue, выделения, CPU/GPU-отображения,
  residency, фиксированные GPU-адреса, отправка команд и подтверждённое
  завершение.
- Раскладка адресного пространства HasVK: окно 16 ГиБ, пулы состояния по
  фиксированным адресам.
- Одно выделение — до 1 ГиБ (минимум спецификации 1.1+), бюджет устройства
  3 ГиБ, до 65536 выделений; проверены одно выделение в 1 ГиБ и 768 МиБ живых
  выделений с записью GPU.
- Ожидание страничной очереди (отображение GPU-адреса и резидентность при
  каждом выделении) — по событию от ядра
  (`D3DKMTWaitForSynchronizationObjectFromCpu`), а не опросом со `Sleep(1)`,
  который стоил целый тик таймера (~15,6 мс) дважды на выделение: создание
  и уничтожение устройства — 13 мс вместо 430 мс, 60 циклов swapchain —
  1,0 с вместо 22,5 с, CTS — ~70–100 тестов/с вместо ~5 (процесс `deqp-vk`
  был занят CPU на 8 %, остальное время ждал).
- Сброса кэша CPU вокруг отправок нет: доступ GPU к памяти, отображённой в
  CPU, когерентен с кэшами CPU (общий LLC). Проверено пробой
  `IrisCoherenceProbe` (`native/tests/coherence_probe.cpp`) без единого
  сброса: буферы 64 КиБ (в L2), 1 МиБ и 4 МиБ; запись CPU → чтение GPU,
  GPU пишет поверх строк, которые CPU прочитал или записал («грязных»), —
  0 расхождений в трёх прогонах; регрессия и выборка CTS без сбросов —
  без отличий. Раньше перед каждой отправкой сбрасывались все отображённые
  буферы целиком (у `vkcubepp` — 7 МиБ и 2,3 мс на отправку); теперь CPU на
  600 кадров `vkcubepp` — 0,94 с вместо 3,41 с, в режиме IMMEDIATE ~545
  кадров/с. `HASVK_WDDM_CPU_FLUSH=1` возвращает сбросы (диагностика).

- Все командные буферы одного `vkQueueSubmit` и запись счётчика завершения
  идут одной отправкой в ядро: хвост каждого буфера при отправке становится
  переходом на следующий. Отдельные отправки — только у ожиданий событий и
  повторно отправленного (simultaneous-use) буфера. Восемь буферов в одной
  отправке: 0,1–0,25 мс на буфер (было 0,52 мс). Проверка порядка — тест
  `submitOrder` в `IrisGraphicsProbe`.
- Неблокирующая очередь: поток очереди не ждёт GPU после отправки;
  отдельный поток завершения ждёт её, проверяет маркеры, защитные области и
  счётчик и сигналит все синхронизации отправки разом. Entry-BO — кольцо из
  64 слотов; командный буфер переиспользуется только после проверки его
  прошлого выполнения. Отправки подряд: 0,77 мс против 1,24–1,30 мс с
  ожиданием каждой (`HASVK_WDDM_SYNC_SUBMIT=1` включает прежний режим).
  Основная цена отправки — планирование в драйвере ядра, поэтому объединение
  буферов даёт больше, чем асинхронность.
- Вывод окна не ждёт GPU (см. 1.4: копия кадра идёт в WSI-отправке через
  очередь). До этого, при отдельной отправке копии, `vkcube` на 1000 кадров
  тратил 8,3 с против 8,7 с с ожиданием каждого кадра и 12,1–12,5 с до
  неблокирующей очереди.
  Отправки, разрезанные ожиданием события, остаются блокирующими: CPU всё
  равно должен увидеть событие перед продолжением.

- MSAA 2x/4x/8x, `vkCmdResolveImage`, blit с линейным фильтром проверены

  одну ячейку при измеренных 287 млн/с на этой GPU (≥2,1 с). Он и остальные
  известные отказы записаны в `docs/cts-expected-failures.md`.
- Командные буферы: цепочка BO без ограничения размера, secondary command
  buffers (копируются в primary).
- Events: отдельный BO; `MI_SEMAPHORE_WAIT` в WDDM-контексте не работает,
  поэтому `vkCmdWaitEvents` вне рендеринга разрезает батч, и очередь ждёт
  события на CPU. Внутри прохода рендеринга ждать нечего: события там могут
  быть установлены только раньше по порядку отправки (установка с хоста после
  отправки запрещена, `VUID-vkCmdWaitEvents-pEvents-01163`), а очередь
  выполняет всё строго по порядку, поэтому остаётся только барьер памяти.
  Проверено режимом 8 теста отрисовки: инстансы записываются передачами,
  событие ставится после них, отрисовка ждёт его внутри прохода — все пиксели
  совпадают.
- Барьеры — штатные HasVK: сбросы и инвалидации кэшей по маскам стадий и
  доступа, а не полный сброс на каждый барьер. CTS `memory.pipeline_barrier`,
  барьеры `synchronization`/`synchronization2`, `synchronization.basic`:
  580 Pass, 0 Fail.
- Потокобезопасность: параллельная запись командных буферов из нескольких
  потоков, выделение памяти, буферов и событий, отправка под мьютексом
  приложения (тест `threads` в `IrisGraphicsProbe`: 4 потока × 40 отправок).
- Два типа памяти, как у upstream HasVK для GPU с общим LLC: тип 0 —
  `DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT | HOST_CACHED` (кэшируемое
  отображение; GPU когерентен с кэшами CPU, см. 1.1), тип 1 — только
  `DEVICE_LOCAL`: выделяется без отображения в CPU (нет `Lock2`, не занимает
  адресное пространство процесса, никогда не сбрасывается). Тест
  `deviceLocalMemory`: `vkMapMemory` отказывает, GPU пишет и копирует.
- Редкий сбой compute 16.11 (`build/failures`, «mismatch at word 16») на
  нынешнем коде не воспроизводится: 1200 итераций того же случая (1000 из
  них без сброса кэша CPU) и 5 прогонов SPIR-V-теста подряд — без сбоев
  (`native/artifacts/compute-rootcause.json`). Сброс кэша на этот случай не
  влияет, то есть тогда помог не он, а вероятнее ожидание настоящего
  завершения GPU, добавленное тем же изменением; исходный код до сбоя в git
  не сохранился, поэтому причина не доказана.
- Потеря устройства (`tools/test-device-lost.ps1`): при настоящем зависании
  GPU (бесконечный compute-шейдер, Windows сбрасывает GPU по TDR) ожидание
  забора возвращает `VK_ERROR_DEVICE_LOST` через ~4,5 с, дальнейшие вызовы
  сразу сообщают о потере и не блокируются, устройство уничтожается, новое
  `VkDevice` в том же процессе работает.
- Адреса буферов (`VK_KHR_buffer_device_address`, A64-доступ); CTS
  `buffer_device_address`, `ssbo.phys`, `physical_pointers`: 629 Pass, 0 Fail.

### 1.3 Шейдеры, compute, графика
- SPIR-V → NIR → ELK → Gen8 для всех стадий: VS, TCS, TES, GS, FS, CS.
- Compute: 3D-группы до 1024 потоков, shared memory, indirect dispatch.
- Графика: vertex input, все формы draw (indexed, instanced, indirect,
  indirect count, multi draw), blending, stencil, depth, MSAA 4x с resolve,
  dynamic state, dynamic rendering, renderpass2, imageless framebuffer.
- 47 форматов (цвет, depth, stencil) и 1D/2D/3D/cube-изображения с
  mip-уровнями и слоями; команды копирования, blit и clear.
- Queries: occlusion, pipeline statistics, timestamp.
- Исправленные ошибки порта, найденные CTS: выравнивание mip-уровней (HALIGN),
  относительная адресация push-буфера 0, события, texel-буферы.
- Исправлено 2026-11-20 (выборки CTS, `docs/cts-expected-failures.md`):
  - точность `sin`/`cos`: математический блок Broadwell возвращает значения
    чуть больше 1 по модулю (`sin(1.58)` = `0x1.0001a8p0`), CTS требует
    [−1, 1]. Включён обход компилятора ELK `precise_trig` (умножение на
    0,99997; brw держит его для всех поколений до Gfx10, кроме KBL);
    `INTEL_PRECISE_TRIG=0` отключает. `glsl.builtin.precision.sin/cos/tan` —
    24 Pass (было 16 Fail), FPS Talos не изменился;
  - несжатый вид сжатого 3D-изображения: Gen8 описывает такой вид только для
    одного слоя, а вид 3D-изображения охватывает все срезы глубины; upstream
    HasVK объявлял поддержку и без проверок утверждений читал
    неинициализированную поверхность (68 падений на каждом 6-м тесте
    `texel_view_compatible.compute.basic.3d_image`). Теперь
    `vkGetPhysicalDeviceImageFormatProperties` отвечает «не поддерживается» для
    3D + сжатый формат + `BLOCK_TEXEL_VIEW_COMPATIBLE`.

### 1.4 Вывод на экран
- `VK_KHR_surface`, `VK_KHR_win32_surface`, `VK_KHR_get_surface_capabilities2`,
  `VK_KHR_surface_protected_capabilities`, `VK_KHR_swapchain`,
  `VK_KHR_swapchain_mutable_format`.
- Форматы поверхности B8G8R8A8 и R8G8B8A8, UNORM и SRGB: B8G8R8A8 копируется
  в поверхность окна как есть, R8G8B8A8 — blit с перестановкой каналов;
  поверхность окна берёт SRGB-вид для SRGB-цепочки, поэтому закодированные
  байты не перекодируются. Запасной путь GDI переставляет каналы на CPU.
- Режимы FIFO, MAILBOX, IMMEDIATE. FIFO после вывода спит до следующего
  vblank по времени композиции DWM (`DwmGetCompositionTimingInfo`,
  высокоточный таймер): 16,7 мс на кадр при 60 Гц — и при включённом, и при
  выключенном экране (`DwmFlush`, проверенный сначала, при выключенном экране
  ждал ~270 мс на кадр, и CTS почти вставал). MAILBOX и IMMEDIATE не ждут —
  2,7–3,4 мс на кадр (раньше единственный FIFO фактически работал как MAILBOX).
- Возможности поверхности по `VK_KHR_win32_surface`: `minImageExtent` =
  `maxImageExtent` = `currentExtent` = клиентская область (upstream объявлял
  1…16384, и CTS создавал цепочку 31×31 в окне 400×300).
- Нехватка памяти при создании swapchain (CTS `simulate_oom`): неудачная
  загрузка шейдера BLORP помечает командный буфер ошибкой
  `VK_ERROR_OUT_OF_HOST_MEMORY` вместо assert в upstream BLORP.
- Размер окна: если клиентская область не совпадает со swapchain, вывод
  возвращает `VK_SUBOPTIMAL_KHR`, а получение кадра — `VK_ERROR_OUT_OF_DATE_KHR`
  (как у других драйверов Windows); пересоздание с `oldSwapchain` работает.
  Свёрнутое окно (0×0) несовпадением не считается: цепочка продолжает
  работать через GDI, а создание цепочки нулевого размера возвращает
  `OUT_OF_DATE` вместо падения (vkcube пересоздавал так и падал на assert).
- Попиксельная проверка кадра (`tools/test-wsi.ps1`, `IrisWsiProbe`, в
  `test-all`): своё окно, которое закрывается само; все четыре формата —
  каждый пиксель клиентской области (снимок `PrintWindow`) совпадает с
  ожидаемым цветом, также после пересоздания цепочки нового размера; все
  кадры прошли перенаправленным выводом, без GDI. При выключенном экране или
  заблокированной сессии (`GUID_CONSOLE_DISPLAY_STATE`, `OpenInputDesktop`)
  DWM не компонует: тот же тест проверяет запасной путь GDI (все форматы тоже
  совпадают попиксельно); темп FIFO одинаков в обоих случаях.
- Копия кадра в отправке WSI проверена и при выключенном экране (отказ ядра
  → повтор без токена → GDI), и при включённом: все кадры теста прошли
  перенаправленным выводом, 0 через GDI.
- Нестандартная геометрия окон (`IrisWsiProbe`): окно без рамки (`WS_POPUP`)
  — перенаправленный вывод, каждый пиксель верен; дочернее окно — через GDI
  в его собственный DC (DWM перенаправляет только окна верхнего уровня, токен
  для дочернего HWND не проверялся), каждый пиксель верен по снимку родителя.
- **Вывод без копии через CPU и без D3D** (`anv_wddm_present.c`): GPU копирует
  кадр (BLORP) в разделяемую поверхность окна, отправка идёт с флагом
  `PresentRedirected` и токеном `(0x80000000 | HWND) << 32 | дескриптор`,
  DWM показывает поверхность. Так выводит кадры OpenGL-драйвер Intel того же
  пакета (снято трассировкой, `tools/trace-gl-present.ps1`). Поверхность
  создаёт наш транспорт по снятому описателю (1096 байт Intel + 104 байта
  данных рантайма): B8G8R8A8, Y-тайлинг, шаг `align(ширина × 4, 128)`, высота
  кратна 32, без отображения в CPU; размер — всё окно с рамкой, кадр
  копируется со смещением клиентской области. Условие — приватные данные
  контекста как у OpenGL-драйвера (без них DWM показывает чёрное); выборка CTS
  с ними — 0 Fail. D3D, Intel UMD и ICD в процессе не загружаются.
- Копия кадра в поверхность окна записывается при `vkQueuePresentKHR` и
  идёт командным буфером в собственной отправке WSI (той, что ждёт семафоры
  приложения), за работой приложения в той же упорядоченной очереди; эта
  отправка в ядро и есть вывод (токен на командном буфере). Нет ожидания
  кадра на CPU и нет отдельной отправки копии: на кадр — одна отправка вывода
  вместо пустой отправки WSI, ожидания её забора на CPU и отдельной копии.
  Командный буфер копии — свой для каждого индекса изображения (WSI ждёт
  прежний вывод того же индекса); при смене размера окна очередь
  дожидается простоя перед заменой поверхности.
- Откат на прежний путь (копия в CPU-буфер + GDI): если ядро отказывает в
  выводе (`PRESENT_OCCLUDED` при спящем экране), поток очереди повторяет ту же
  отправку без токена, а следующий кадр идёт через GDI (с ожиданием его копии
  на CPU); затем снова пробуется вывод. `HASVK_WDDM_PRESENT=gdi` включает GDI
  принудительно.
- Неизменённый `vkcube`: 40 с с resize и minimize под validation layers —
  3063 кадра через поверхность окна, 0 через GDI, 0 ошибок; окна от 200×150
  до 1280×720, в том числе частично за краем экрана (GDI там рисовал пусто).
- Проверки: `tools/test-present-redirect.ps1` (своя поверхность, цвета и
  раскладка по пикселям экрана), `tools/capture-vkcube.ps1 -Present redirect|gdi`.
- Несколько мониторов с разным масштабом не нужны (решение пользователя): на
  этой машине один монитор 2560×1600 при 100 %.

### 1.8 Производительность (этап 7, состояние на 2026-11-20)

The Talos Principle, встроенный бенчмарк (Demo, 30 с, 640×480, одинаковые
авто-настройки), `tools/run-talos.ps1`: **Vulkan 27,8 → 70–83 FPS** (чаще
75–79), DX11 в тех же сериях — 79–87 FPS (отношение 0,87–0,96 в парах
прогонов; 2026-11-19, в более прохладном состоянии машины, было 79–83 против
83–91). 1 % худших кадров: ~20 → 24–35 FPS (DX11 — 30–40). Измерения,
гипотезы, отклонённые опыты и порядок замеров — `docs/optimizations-vs-dx11.md`.

**Где разрыв (2026-11-20).** Кадр под обоими API задаёт главный поток игры
(87–90 % времени занят). Драйвер обходится ему дешевле драйвера Intel DX11
(≈2,0 против ≈3,4 мс на кадр), но путь Vulkan игры строит тени заново каждый
кадр, GPU занят 81–91 % против 73–77 %, и из-за общего бюджета питания CPU
работает на 4–19 % медленнее — код игры идёт дольше. На одинаковой работе
драйвер вровень с драйвером Intel.

**Разбор сохранённых журналов** (`docs/optimizations-vs-dx11.md`, раздел 1.9).
По собственной разбивке игры ~90 % разрыва — в секциях shadows (+0,8 мс) и
misc (+0,4 мс) главного потока, секция scene совпадает. Вызов ядра для вывода
кадра в 27–40 % кадров длится 9–11 мс: ядро держит его, пока GPU не закончит
прошлый кадр; в этих же кадрах главный поток ждёт `vkGetQueryPoolResults`
0,7–1,0 мс. Кадры от этого не длиннее, так что развязка вывода и очереди ради
Talos не нужна.

**Замер потоков и кода под обоими API** (шесть прогонов, там же, раздел 1.10).
Главный поток, мс на кадр, DX11 (84,3 FPS) против Vulkan (73,5 FPS): код игры
6,19 против 8,46; драйвер с вызовами ядра 3,37 против 2,35. Драйвер дешевле
драйвера Intel на ~1,0 мс, код самой игры идёт на 2,27 мс дольше: путь Vulkan
игры дороже её пути DX11 (1,43 против 0,77 мс), общий код замедлен в 1,27
раза. Главный поток ждёт не драйвер, а ответа Steam (под обоими API). Лишние
32 % логического CPU под Vulkan — поток `VLKSupportThread` самой игры с циклом
без ожидания (~20 %), поток очереди драйвера (8 %) и поток завершения.

**Вывод.** Паритет требует −1,75 мс главного потока на кадр, а драйверу на
нём принадлежит 2,15 мс: универсальными исправлениями драйвера ни обогнать
DX11 в Talos, ни сравняться с ним нельзя. Разрыв задаёт путь Vulkan самой
игры: её код на главном потоке, её поток с циклом без ожидания и тени заново
каждый кадр на GPU. Запись draw разобрана повторно: пропускать повторное
применение состояния конвейера нечем (из 111 смен конвейера в проходе теней ни
одна не ведёт к конвейеру с тем же состоянием).

### 1.10 Полный прогон CTS (этап 4)

- Полный mustpass `vk-default` CTS 1.4.5.5 (`tools/run-cts-full.ps1`,
  2026-11-20, 8,5 часа, по два процесса, сборка до исправлений): из 2 888 682
  тестов выполнено 2 849 001 — Pass 669 179, NotSupported 2 179 726,
  QualityWarning 6, Fail 85, ResourceError 5
  (`native/artifacts/cts-full-20261120.json`). 19 681 теста списка в этой
  сборке `deqp-vk` нет; первая часть `draw` (20 000 тестов) досчитана отдельно
  на исправленной сборке: 14 047 Pass, 5953 NotSupported.
- По итогам исправлено девять ошибок драйвера
  (`docs/cts-expected-failures.md`, раздел «Исправлено»):
  - зависание видеодвижка на шейдерах с режимом `DepthUnchanged`
    (`execution_mode.depthunchanged_0`, `_2`). Причина — не железо, а правило
    Microsoft: битовое поле с типом перечисления знаковое. Трёхбитное поле
    `depth_layout` в `shader_info` возвращало −4 вместо 4
    (`FRAG_DEPTH_LAYOUT_UNCHANGED`), компилятор ELK сообщал «глубина не
    вычисляется», а шейдер глубину писал; такое расхождение состояния и
    сообщения записи вешает железо. Перечислениям `shader_info` в узких полях
    задан беззнаковый тип, как раньше перечислениям ELK. Найдено временными
    отметками хода в командном буфере (GPU записывал номер шага перед каждой
    отрисовкой) и заменой в проходящем тесте одного только режима шейдера;
  - шейдеры со сбросом регистров не имели буфера сброса: число потоков,
    владеющих буфером (`max_scratch_ids`), заполняет только Linux-часть Mesa, и
    порт отклонял флаг «адрес в пределах 4 ГиБ». Неверные результаты (42 теста
    `graphicsfuzz`, 13 тестов подгрупп, в том числе давний отказ
    `clustered…i64vec4`, `opphi.wide`) и зависания видеодвижка. Буферы сброса
    теперь лежат в своём диапазоне первых 4 ГиБ окна адресов GPU, указатель —
    смещение от General State Base Address;
  - `u_memstream` Mesa на Windows оставлял временный файл на каждую компиляцию
    шейдера (65 535 файлов в `%TEMP%`, после чего компиляция шла секундами);
    файл теперь удаляется при закрытии;
  - `vkCreateBuffer` не учитывал `VkBufferUsageFlags2CreateInfo`, а создание
    графического конвейера — `VkPipelineCreateFlags2CreateInfo`
    (`VK_KHR_maintenance5`);
  - `VK_ACCESS_2_SHADER_STORAGE_READ_BIT` не сбрасывал кэши (20 тестов
    `synchronization2`);
  - командный буфер получает первый BO и блок таблиц привязок при начале
    записи, а не при создании (10 000 командных буферов сразу); слотов событий
    65 536 вместо 4096;
  - 64-битный вершинный атрибут шире, чем читает шейдер, выбирается как
    R64G64 (раньше сдвигал поток вершин).
- Из 90 непрошедших тестов проходят 89. Итоговая проверка на текущей сборке
  одним запуском (все 90 тестов): 89 Pass, 1 Fail — ожидаемый
  `conformance_version` (`native/artifacts/cts-rerun-failed-20261120.json`).
  Соседние группы после правок: 1939 Pass, 0 Fail (конвейеры и вершинные
  атрибуты) и 714 Pass, 0 Fail (глубина из шейдера, ранние тесты фрагментов,
  проверка глубины). Тестов, исключённых из-за зависаний, больше нет.
- Запускалка: `run-cts.ps1` продолжает прогон по множеству тестов без
  результата (`deqp-vk` выполняет список в своём порядке и при любом отказе
  завершается с ненулевым кодом; прежний учёт «после последнего теста»
  зацикливался), `-Jobs N` раздаёт тесты по процессам и перепрогоняет
  непрошедшее в одном (на 2934 тестах `pipeline.monolithic`: 40,8 с в один
  процесс, 30,8 с в 2, 27,8 с в 3). `run-cts-full.ps1` режет mustpass на части

## 2. Осталось

**Конечная цель (решение пользователя, 2026-11-20):** играть в Dota 2 под
Vulkan с FPS выше, чем под DX11. The Talos Principle был испытательным
стендом: работающая игра с обоими API и встроенным бенчмарком.

### Этап 8 (главный). Dota 2 под Vulkan

Ничего из этого этапа ещё не делалось. На 2026-11-20 игра не установлена
(от неё осталась пустая папка `dota 2 beta`), на диске свободно 42 ГиБ, а игра
занимает около 60 ГиБ.

1. Переустановить ICD: обычный запуск игры берёт установленную копию, а она
   отстаёт на исправление зависания `DepthUnchanged` (раздел 1.9). Запуск
   `tools\install-icd.ps1` от имени администратора подтверждает пользователь.
2. Установить Dota 2 и бесплатное дополнение с поддержкой Vulkan (действие
   пользователя в Steam; нужно освободить место).
3. Пробный запуск под нашим драйвером: доходит ли игра до меню и матча.
   Vulkan включается ключом `-vulkan` или в настройках видео (нужен
   перезапуск), после установки дополнения «Dota 2 - Vulkan Support»; ключи
   `-dx9`/`-dx11`/`-gl` из параметров запуска убрать. Признак того, что
   работает именно Vulkan, — в консоли есть команда `vulkan_memgr_print`.
4. Повторяемый замер. Встроенного бенчмарка одной кнопкой, как в Talos, нет;
   меряют проигрыванием записи матча. Команды по руководству GamingOnLinux
   (2016, для Linux; на текущем клиенте Windows не проверены):
   `-vulkan +timedemo <запись> +demo_quitafterplayback 1 +fps_max 0
   -autoconfig_level 3 -w <ширина> -h <высота> -fullscreen`, отрезок —
   `+timedemo_start <тик> +timedemo_end <тик>`; запись лежит в `game\dota`;
   итог дописывается в `game\dota\Source2Bench.csv` (средний FPS и
   разброс), поэтому файл перед каждой серией убирать. DX11 — тем же набором
   с `-dx11`. Графические настройки при смене API могут меняться —
   `-autoconfig_level` задаёт их одинаково. Запись должна быть от текущей
   версии игры (записи 2016 года не подойдут). Скрипт — по образцу
   `tools/run-talos.ps1`.
5. Сравнение DX11 и Vulkan чередованием прогонов и разбор теми же
   инструментами (журнал кадра, замер окна, сэмплер, профиль проходов).

Что известно о требованиях игры (2026-11-20, по открытым источникам, без
запуска):
- Трекер Valve `ValveSoftware/Dota-2-Vulkan`: минимум для Windows — NVIDIA
  Kepler и новее или AMD 7700 и новее, 2 ГБ памяти GPU («с меньшим объёмом
  возможны падения»). **Intel в списке для Windows нет** — у Intel для этого
  поколения под Windows не было драйвера Vulkan. Проверяет ли клиент Windows
  производителя или версию драйвера, неизвестно: это покажет только запуск.
- Под Linux с марта 2023 года игра работает только через Vulkan, минимум —
  Intel HD 5000-й серии (GamingOnLinux), то есть это же поколение GPU с тем
  же семейством драйвера (HasVK). Значит, набора возможностей HasVK рендеру
  Source 2 в принципе хватает.
- Наш драйвер сообщает (vulkaninfo, `build\icd`): Vulkan 1.3, одна куча
  памяти на 3 ГиБ (требование 2 ГБ выполнено), сжатие BC, 107 расширений;
  `VK_EXT_memory_budget` нет.
- Список расширений, которые запрашивает рендер, в открытых источниках не
  найден.

Ограничения:
- **VAC.** Сэмплер приостанавливает потоки игры и читает её память, прокси
  `d3d11.dll` кладётся в папку игры: только при запуске с `-insecure`, на
  записях и с ботами. Как античит отнесётся к самодельному драйверу Vulkan в
  обычной сетевой игре, неизвестно; это риск для аккаунта и решение
  пользователя.
- Вывод по Talos на Dota не переносится: там отставание задавал путь Vulkan
  самой игры, у Source 2 рендер другой.
- Только универсальные исправления драйвера, без профилей под игры.

### Этап 7. Vulkan быстрее DX11 в The Talos Principle

**Итог (2026-11-20, раздел 1.8).** Vulkan 70–83 FPS (чаще 75–79) против
79–87 у DX11. Паритет требует −1,75 мс главного потока на кадр, а драйверу на
нём принадлежит 2,15 мс: универсальными исправлениями драйвера ни обогнать
DX11 в Talos, ни сравняться с ним нельзя. Решение о закрытии этапа — за
пользователем.

Что осталось непроверенным или несделанным (ожидание низкое):
1. Локальные ускорения записи draw. Сделано 2026-11-20: состояние
   поверхности динамического буфера по шаблону с самопроверкой против ISL —
   запись draw на стенде 931–941 нс против 981–997 (−5 %), в Talos выигрыш в
   пределах разброса (`docs/optimizations-vs-dx11.md`, «B2, повторно»). Не
   сделано: адреса буферов вершин без обращения к BO (~2 % стенда, риск для
   учёта зависимостей буферов).
2. E7 — вызов ядра для вывода кадра: 0,83 мс CPU потока очереди на кадр
   против ~0,05 мс у `Present` DX11. Путь вывода как у DXGI
   (`D3DKMTPresent`) — исследование закрытого интерфейса; выигрыш косвенный.
3. C5 и C6 — работа GPU в основном проходе и в тенях: дорого (на том же draw
   листвы драйвер Intel не быстрее).

Метод, команды для каждого замера и меры безопасности —
`docs/optimizations-vs-dx11.md`, разделы 5–7.

### Этап 4. CTS

Полный прогон выполнен, все найденные им ошибки исправлены (раздел 1.10).
Осталось:
1. Повторный полный прогон на исправленной сборке (8–9 часов) — по решению
   пользователя не выполняется; запущенный 2026-11-20 остановлен на 60 000
   тестах без отказов.
2. Знаковые битовые поля-перечисления (причина зависания `DepthUnchanged`)
   проверены поиском в каталогах Intel, входящих в сборку (ELK, HasVK, ISL,
   BLORP, `common`, `dev`), и в общих заголовках шейдеров (`shader_info.h`,
   `shader_enums.h`, `glsl_types.h`): оставшиеся поля вмещают свои значения.
   NIR и общий рантайм Vulkan отдельно не проверялись — их upstream сам
   собирает компилятором Microsoft. Каталоги, которые войдут в сборку позже
   (например, `brw`), проверять так же.

## 3. Риски

- **Зависание GPU может уронить систему.** Зависший видеодвижок Windows
  сбрасывает сама (отчёт LiveKernelEvent 141, приложение получает
  `VK_ERROR_DEVICE_LOST`), но драйвер ядра Intel `20.19.15.5171` после такого
  сброса дважды закончил критической ошибкой: 0x119 (2026-11-20 01:06) и 0xD1
  (13:38). Всего отчётов 141 за время работы — около 50. Обе найденные
  причины зависаний (шейдеры со сбросом регистров без буфера сброса; шейдеры
  с режимом `DepthUnchanged`) исправлены, известных зависающих тестов CTS не
  осталось; неизвестные причины возможны. Опыты, которые заведомо вешают
  GPU, — только с согласия пользователя; число отчётов до и после прогона — в
  папках `Kernel_141_*` каталогов `C:\ProgramData\Microsoft\Windows\WER`.
- **Цель «быстрее DX11» зависит от игры.** В Talos она недостижима
  универсальными исправлениями драйвера (этап 7); для Dota 2 ничего не
  измерено. Общий бюджет питания CPU и GPU этого процессора (2 ядра, 28 Вт)
  ограничивает оба API.
- **Античит.** Инструменты профилирования и самодельный драйвер в процессе
  игры с VAC (этап 8).
- **Закрытый интерфейс Intel** — описан и ограничен одной версией драйвера
  (раздел 1.6): на другой ICD безопасно не включается. Остаётся неизвестным,
  насколько значения стабильны между версиями, — проверить нельзя без другой
  версии драйвера; перенос — по `docs/intel-interface.md`.
- **Вывод без CPU-копии** — снят: вывод через перенаправленную отправку
  работает в ICD без D3D (раздел 1.4). Остаточный риск — описатель
  поверхности снят с одного драйвера, как и остальные описатели.
- **Ограничения ядра** — проверены (раздел 1.5): кроме `MI_SEMAPHORE_WAIT`
  запретов нет. Остаточный риск — команды, которых HasVK пока не использует
  в нашей конфигурации (perf-запросы с настройкой OA-регистров).
