# Производительность: Vulkan против DX11 на Iris 6100

Рабочий документ главного этапа 7 (`docs/roadmap.md`): сделать Vulkan быстрее
DX11 в The Talos Principle. Допустимы только универсальные исправления
драйвера, без профилей под отдельные игры (решение пользователя).

Здесь: измерения (раздел 1), **список гипотез для проверки** (раздел 2),
проверенное и отклонённое (раздел 3), методика (раздел 4). Сделанные
оптимизации перечислены в roadmap, раздел 1.8; инструменты — там же, раздел 1.7.

Состояние на 2026-11-19. Метки вида 2.1–2.10 — прежние номера тем этого
документа; на них ссылаются roadmap и комментарии в коде, поэтому они
сохранены.

## 1. Где мы сейчас

Встроенный бенчмарк (`tools/run-talos.ps1`: Demo, 30 с, 640×480, одинаковые
авто-настройки), прогоны чередованием в одном состоянии машины:

| | DX11 (драйвер Intel) | Vulkan (HasVK/WDDM) |
|---|---|---|
| Средний FPS | 83–91 | 79–83 (в начале этапа — 27,8) |
| 1 % худших кадров | 39–42 FPS | 30–37 FPS |
| Время кадра в замере загрузки GPU | 11,5 мс (86,6 FPS) | 12,95 мс (77,2 FPS) |
| GPU занят (счётчик Windows «GPU Engine Utilization», 3D) | 74,1 % — 8,6 мс на кадр | 84,7 % — 11,0 мс на кадр |

Отношение Vulkan к DX11 — 0,89–0,95 в зависимости от состояния машины.

### 1.1 Главное наблюдение: под Vulkan простаивают и GPU, и поток игры

- GPU занят 85 % времени: около 2 мс каждого кадра он стоит без работы.
- Главный поток игры занят ~85 % ядра (`rip_sampler`); драйвер на его стеке —
  ~20 % выборок, то есть ~2,2 мс на кадр.
- Работа GPU за кадр Vulkan (11,0 мс) **меньше всего кадра DX11** (11,5 мс).

Вывод: если бы GPU получал работу без промежутков, кадр Vulkan занял бы
~11,0 мс (около 91 FPS) — это быстрее DX11 без сокращения работы GPU. Поэтому
первой идёт группа A раздела 2: найти, почему CPU и GPU ждут друг друга.

Оговорки. Загрузка потока и загрузка GPU сняты в разных прогонах. То, что
DX11 упирается в CPU игры, — вывод из простоя GPU (26 %), загрузка его
главного потока не мерилась. CPU и GPU делят общий бюджет питания: при
большей загрузке GPU поток игры может замедлиться.

### 1.2 Время GPU по проходам

| Проход | DX11, мс | Vulkan, мс |
|---|---|---|
| 2 карты теней 1536² (D16) | 2,4 | ~5,2 |
| Основной 640×480 (RGBA16F + D32) | 3,5 | ~2,9 |
| Предпроход (R16F + D32) | 1,7 | ~1,1 |
| Пост-обработка, копии | ~1 | ~1,5 |
| Сумма | 8,6 | ~10,7 |

Столбец DX11 снят раньше прокси `d3d11.dll` (при ~80 FPS с прокси), столбец
Vulkan — профилем проходов после всех исправлений; суммы сходятся со
счётчиком Windows (8,6 и 11,0 мс). По этим числам вне теней Vulkan не отстаёт,
а весь разрыв по GPU — тени. Сравнение проходов в одном состоянии машины не
повторялось.

Тени, статистика конвейера на одну карту:

| | DX11 | Vulkan |
|---|---|---|
| Вершин на входе | 384 тыс. | 429 тыс. |
| Вызовов VS | 161 тыс. | 181 тыс. |
| Вызовов PS/FS | 7 тыс. | 3 747 тыс. |

Путь DX11 игры не очищает карты теней и переиспользует их между кадрами:
draw почти целиком отбрасываются ранним тестом глубины. Путь Vulkan каждый
проход очищает карту и строит её заново с альфа-тестом (`discard`) в FS. На
микротесте с одинаковой работой счётчики обоих драйверов совпадают, настройка
игры `vlk_iEmulateAlphaTest 0` число вызовов не меняет. Это выбор игры;
драйвер может только удешевить ту же работу (гипотеза C6).

### 1.3 Одинаковая работа на обоих драйверах (микротесты)

| Тест | Vulkan | D3D11 Intel | Отношение |
|---|---|---|---|
| VS: 4 итерации × 3 `texelFetch` (как листва Talos) | 487 Мверш/с | 487 Мверш/с | 1,00 |
| Пустой VS (фиксированный путь вершин, 2.9) | 948 Мверш/с | 1063 Мверш/с | 0,89 |
| 1000 draw по 3 вершины без смены состояния | 0,11 мкс/draw | 0,08 мкс/draw | — |
| Сэмплер при прогретой частоте GPU | 18,8 Гвыб/с | 19,8 Гвыб/с | 0,95 |
| Цикл FMA, 250 запусков | 442 GFLOPS | 525 GFLOPS | 0,84 |
| 8 слоёв с `discard` в D16 1536², с `HASVK_WDDM_NO_HIZ_SAMPLING=1` | 1,62 и 5,20 мс | 1,63 и 5,34 мс | 1,0 |
| Один draw листвы из игры (`replay_probe`) | — | не быстрее | ~1,0 |
| Заливка только глубины, без FS | 22 Гпикс/с | 53 Гпикс/с | 0,42 — снято до исправлений очистки HiZ, перемерить (C2) |

У Vulkan разброс между запусками больше (выборка 16,4–18,8 Гвыб/с против
19,5–19,8 у D3D11) — см. гипотезу A5.

## 2. Гипотезы для проверки

Порядок — по ожидаемому выигрышу в FPS и цене проверки. Группа A возможна
только как исправление драйвера и не требует обгонять драйвер Intel на
одинаковой работе, поэтому она первая.

| № | Гипотеза | Что даст, если верна | Цена проверки |
|---|---|---|---|
| A1 | Временная шкала кадра покажет, кто кого ждёт | Сама ничего; выбирает A2–A4 | Низкая: только профилировщик |
| A2 | Запись команд вдвое медленнее рядом с отправками | До ~1 мс потока игры на кадр и больше | Низкая: стенд есть |
| A3 | Слишком много вызовов ядра на кадр | Время потока отправки на двух ядрах | Низкая, исправление — средняя |
| A4 | Сигнал о завершении GPU приходит с задержкой | Длина очереди «CPU впереди GPU» | Средняя |
| A5 | Под Vulkan GPU работает на пониженной частоте | Пропорционально частоте | Средняя |
| A6 | DWM тратит на наш вывод больше, чем на вывод DX11 | Неизвестно, вероятно мало | Низкая |
| C2 | Заливка только глубины медленнее драйвера Intel | Тени и предпроход | Низкая: пробы есть |
| C1 | Обход PMA можно не выключать для непрозрачных draw с FS | До ~1 мс GPU на кадр | Средняя, риск по корректности |
| C4 | Варианты генерации кода ELK (проверки недействительны) | ~0,4 мс на 10 % кода FS | Средняя |
| C3 | Мелкие проходы дороже, чем у DX11, из-за сбросов на границах | До ~0,5 мс GPU | Низкая |
| B1 | В кадре есть горячие точки драйвера вне записи draw | По ~1 % кадра на точку | Низкая |
| B3 | Сборка драйвера под Broadwell, LTO, PGO | Несколько процентов CPU драйвера | Низкая |
| B2 | Четыре известных горячих места записи | По ~1 % потока игры | Средняя |
| C5 | Код FS основного прохода у драйвера Intel быстрее нашего | Указывает, нужен ли разбор ELK | Высокая |
| C6 | Ту же работу в тенях можно сделать дешевле | До ~0,7 мс, ожидание низкое | Высокая |
| D1–D3 | Медленные кадры привязаны к выделениям и кэшам | 1 % худших кадров | Низкая |
| C7 | Барьеры, L3/MOCS, путь вершин, цикл FMA | Мало | Разная |

Что считать успехом группы A: загрузка GPU по счётчику Windows растёт с 85 %
к 95–100 % при той же работе GPU на кадр. Если после этого GPU занят
полностью, FPS дают только пункты группы C; если упор окажется в CPU —
группа B.

### Группа A. CPU и GPU ждут друг друга (~2 мс на кадр)

**A1. Временная шкала кадра.** Наблюдение — раздел 1.1.
Проверка: добавить в профиль (`HASVK_WDDM_PROFILE_PASSES`) на каждый кадр:
1. сколько поток игры стоит внутри драйвера, по точкам входа
   (`vkAcquireNextImageKHR`, `vkQueuePresentKHR`, `vkWaitForFences`,
   `vkGetFenceStatus`, `vkGetQueryPoolResults`, `vkQueueSubmit`,
   `vkAllocateMemory`) и на мьютексах устройства;
2. задержку каждой отправки от постановки в очередь до возврата
   `D3DKMTSubmitCommand`;
3. начало и конец работы GPU по каждой отправке (метки `TIMESTAMP` в буфере
   команд профиль уже ставит);
4. задержку от конца работы GPU до сигнала fence потоком завершения.

Контроль: загрузка главного потока под DX11 (`rip_sampler`), чтобы отличить
ожидания самой игры от ожиданий в драйвере. Результат — ответ, почему GPU
остаётся без работы: поздняя отправка (A3), ожидание игры на fence или
запросах (A4), блокировка потоков (A2) или порог очереди кадров (тогда A/B
глубины очереди: 2 против 3 изображений).

**A2. Запись команд вдвое медленнее рядом с отправками.**
Наблюдение: на стенде `replay_pass_probe` драйвер тратит ~1,1 мкс на draw при
записи без отправок и ~2 мкс, когда запись чередуется с отправками. Процессор
— 2 ядра, 4 потока (i5-5257U). Возможные причины: (а) общий бюджет питания
CPU и GPU; (б) поток отправки и поток завершения делят с потоком игры два
ядра, в том числе как сосед по Hyper-Threading; (в) вызовы ядра вытесняют
кэши; (г) блокировки между потоками.
Проверка: `REPLAY_RECORD_ONLY` в пяти условиях — без нагрузки; при нагрузке
GPU из другого процесса (питание без наших потоков); со своими отправками в
обычном режиме и с `HASVK_WDDM_SYNC_SUBMIT=1`; с привязкой служебных потоков
к другому ядру.
Если подтвердятся (б)–(г): размещение и приоритет служебных потоков, одно
пробуждение потока завершения на кадр вместо пробуждения на каждую отправку,
короче критические секции. Причина (а) драйвером не лечится, но тогда любое
сокращение работы CPU или GPU ускоряет и вторую сторону.
Ожидание: если то же замедление действует на код игры (~9 мс на кадр), а не
только на драйвер (~2 мс), выигрыш больше 1 мс.

**A3. Меньше вызовов ядра на кадр.**
Наблюдение: `D3DKMTSubmitCommand` стоит 0,25–0,77 мс CPU в потоке отправки,
вывод кадра — ~1,1 мс. Объединяются только командные буферы одного
`vkQueueSubmit`; разные `vkQueueSubmit` и копия кадра для вывода идут
отдельными вызовами. Сколько отправок на кадр делает Talos — не считали.
Проверка: счётчик отправок и суммарное время потока отправки на кадр.
Если отправок больше двух на кадр: объединять стоящие в очереди отправки и
копию вывода в один вызов ядра, когда поток отправки отстаёт.

**A4. Задержка сигнала о завершении.**
Наблюдение: поток завершения ждёт объект ядра, проверяет маркеры, защитные
области и счётчик и только потом сигналит. Если игра сама ждёт fence или
результаты запросов прошлых кадров (покажет A1), эта задержка напрямую
превращается в простой.
Проверка: гистограмма задержки «конец работы GPU — сигнал»; отвечают ли
`vkGetFenceStatus` и `vkGetQueryPoolResults` по счётчику завершения в памяти
или ждут поток завершения.
Если подтвердится: отвечать по счётчику напрямую, будить ожидающих до
проверок.

**A5. Частота GPU под Vulkan.**
Наблюдение: результаты микротестов Vulkan разбросаны сильнее, чем D3D11
(раздел 1.3). Предположение: промежутки простоя между отправками удерживают
GPU на пониженной частоте (частотой управляет драйвер ядра).
Проверка: читать фактическую частоту в кадре — регистр RPSTAT (по i915 адрес
0xA01C, поле CAGF; адрес и поле сверить с `i915_reg.h`) командой
`MI_STORE_REGISTER_MEM`. Разрешено ли чтение в нашем контексте — проверить
способом `test-kernel-limits`. Сравнить Talos (85 % занятости) с длительным
микротестом (100 %).
Если частота в Talos ниже: драйвер ею не управляет, лечится только
устранением простоев (A1–A4); результат даёт оценку выигрыша.

**A6. Доля DWM.**
Наблюдение: наш вывод — перенаправленная поверхность, которую DWM компонует
каждый кадр; поверхность создаётся на всё окно с рамкой.
Проверка: счётчик «GPU Engine» по процессам (`dwm.exe` и игра) и CPU
`dwm.exe` при Vulkan и при DX11.

### Группа B. CPU драйвера в потоке игры (~2,2 мс на кадр)

Даёт FPS, только если после группы A упор окажется в CPU.

**B1. Профиль всего кадра по точкам входа.** Стенд записи покрывает один
проход теней. `rip_sampler` со стеками в Talos: доля каждой точки входа
Vulkan в потоке игры — запись draw, дескрипторы, начало и конец прохода
(операции BLORP и HiZ), сброс и начало буферов команд, отображение памяти.

**B2. Известные горячие места стенда `REPLAY_RECORD_ONLY`:**
`vk_dynamic_graphics_state_copy` в `vkCmdBindPipeline` (~6 % записи),
`gfx8_cmd_buffer_flush_dynamic_state` (~5 %), заполнение surface state
динамических UBO в `emit_binding_table` (~5 %), `vkCmdBindVertexBuffers2`
(~3 %). Каждое — около 1 % потока игры, в FPS Talos ниже разброса.

**B3. Параметры сборки драйвера.** Сейчас `debugoptimized` (O2 с отладочной
информацией), без LTO, без наборов команд выше базового x86-64. Цель — одна
машина: `/arch:AVX2` (или `-march=broadwell`), LTO для ICD, затем PGO по
`replay_pass_probe`. Проверка: `REPLAY_RECORD_ONLY` (разброс ~1 %), затем
Talos. Новая сборка меняет UUID кэша, первый прогон после неё холодный.

### Группа C. Работа GPU (11,0 мс на кадр)

Даёт FPS, когда GPU загружен полностью: 1 мс — около 8 % FPS.

**C1. Обход PMA: не выключать для непрозрачных draw с FS (2.5).**
Наблюдение: ~59 переключений обхода за кадр, каждое — остановка командного
потока, которой требует PRM перед записью `CACHE_MODE_1`. Постоянно
включённый обход (опыт только для измерения, ранние числа) ускорял основной
проход с 3,9 до 2,5 мс и предпроход с 1,8 до 1,35 мс, но замедлял тени с 4,7
до 7,7 мс на карту. В тенях обход был лишним для draw без FS; пострадали ли
от него непрозрачные draw с FS — не выяснено. Отклонённые варианты (раздел 3)
эту часть не проверяли.
Проверка: микротест на `depth_fill_probe` с принудительным состоянием обхода
для трёх видов draw — без FS, непрозрачный с FS, с `discard` — и отдельно цена
одного переключения (N чередований). До реализации сверить с PRM Broadwell
(`CACHE_MODE_1`), допустим ли включённый обход вне условий, при которых он
обязателен.
Если непрозрачным draw с FS включённый обход не вредит: выключать его только
перед draw без FS. Обязательны выборки CTS по глубине, трафарету и
`fragment_operations`.
Ожидание: до ~1 мс GPU на кадр в основном проходе и предпроходе.

**C2. Заливка только глубины против драйвера Intel.**
Наблюдение: в документах осталась цифра 22 против 53 Гпикс/с
(`depth_fill_probe` и `d3d11_depth_fill_probe`), снятая до исправлений
быстрой очистки HiZ. Тени и предпроход — как раз такие проходы.
Проверка: перемерить обе пробы на нынешней сборке по слоям (первый после
очистки, видимый, скрытый), с обычной и обратной глубиной.
Если разрыв остался: сравнить состояние `3DSTATE_WM`, `3DSTATE_PS_EXTRA`,
раннего теста глубины и HiZ с тем, что нужно проходу без FS.

**C3. Мелкие проходы пост-обработки.**
Наблюдение: ~1,5 мс против ~1 мс у DX11 на небольших проходах, трёх копиях и
блитах.
Проверка: время каждого мелкого прохода и причины сбросов и остановок на его
границах (профиль проходов их уже считает); микротест «N проходов по одному
draw» против D3D11.

**C4. Повторить проверки генерации кода (2.2).**
Наблюдение: до 2026-11-19 `pipelineCacheUUID` был постоянным, и кэш игры
отдавал новой сборке двоичный код старой. Выводы «не рычаг» получены на
старых шейдерах и недействительны: `INTEL_DEBUG=no8` (без SIMD8 там, где есть
SIMD16; было 37,4 против 37,6 FPS), чтение UBO блоком через константный кэш.
Не проверялись вовсе: порядок эвристик планировщика ELK, `INTEL_DEBUG=no16`.
Подготовка: UUID зависит только от файла DLL, поэтому варианты через
переменную окружения делят один кэш. Нужно добавить значение `INTEL_DEBUG` (и
прочих переключателей генерации кода) в UUID.
Проверка: на вариант — холодный и тёплый прогон, не меньше двух раундов.

**C5. FS основного прохода: наш код против кода драйвера Intel.**
Проверка: снять один тяжёлый draw основного прохода в обоих API (под DX11 —
прокси: DXBC, состояние, текстуры), воспроизвести полноэкранно, сравнить
время на миллион пикселей. Шейдеры у путей игры разные, но делают одно и то
же. Если драйвер Intel быстрее более чем на 10 % — разбирать ELK: планировщик,
давление регистров, SIMD16.

**C6. Тени: удешевить ту же работу.**
Наблюдение: FS альфа-теста стоит ~1 мс на карту при 3,7 млн вызовов — заметно
медленнее пропускной способности сэмплера на крупных примитивах; вероятная
причина — мелкие треугольники, поток FS на несколько пикселей. Вершинный
путь: 8 вершинных элементов на вершину листвы, перенос данных экземпляра из
VF в шейдер даёт оценку сверху −0,33 мс на карту.
Ожидание низкое: на том же draw листвы драйвер Intel не быстрее.

**C7. Низкое ожидание.**
- Перевод барьеров в `PIPE_CONTROL` (2.6): лишние сбросы кэша глубины для
  не-глубинных изображений; `vlk_bNoBarriers` FPS не меняет.
- L3 и MOCS (2.7): сравнить конфигурацию с драйвером Intel; сэмплер уже 0,95.
- Фиксированный путь вершин (2.9): 0,89 на пустом VS, с работой в VS разница
  исчезает; смотреть разбиение URB, размер VUE, `3DSTATE_VF`.
- Цикл FMA (2.7): 0,84; вынос констант из циклов на настоящих шейдерах
  вреден (раздел 3), нужен другой способ или более представительный тест.

### Группа D. 1 % худших кадров

- **D1.** A/B файлов кэша шейдеров: с ними и с `HASVK_WDDM_INTERNAL_CACHE=0`.
  В тёплых прогонах компиляций 0, но отдельного сравнения не было.
- **D2.** Привязать кадры 45–80 мс ко времени событий: выделения
  (`CreateAllocation2` сам ждёт очередь подкачки ядра, до 90 мс за 5 с при
  загрузке), компиляции, длительность вызовов ядра. Источники: времена кадров
  игры (`Temp\BenchFrames_*.csv`) и метки профиля драйвера.
- **D3.** Время создания устройства при большом `default-cache.bin` (файл
  читается целиком, предел 64 МиБ; CTS тоже его наполняет).

### Вне списка

- Свой путь теней игры под Vulkan (раздел 1.2): исправим только профилем под
  игру, что исключено.
- Ускорение прогона бенчмарка своим скриптом: игра принимает только
  подписанные скрипты, защиту не обходим.

## 4. Методика и подводные камни

- Разброс FPS Talos ±5 %: сравнивать только чередованием сборок в одном
  состоянии машины, не меньше 3+3 прогонов. Машина «разогревается» по ходу
  серии, FPS растёт к концу.
- Первый прогон после новой сборки холодный: игра перекомпилирует все
  конвейеры (461 компиляция, 1 % худших ~7 FPS). Его не учитывать.
- Изменения генерации кода сравнивать только сборками с разными UUID (C4).
- Микротесты (`flops_probe`, `replay_pass_probe` и другие) создают конвейеры
  без кэша приложения, но берут их из `default-cache.bin`; при сравнении
  вариантов компилятора на одной DLL ставить `HASVK_WDDM_INTERNAL_CACHE=0`.
- Тестовый бот игры иногда завершает уровень через ~2 с; `run-talos.ps1`
  распознаёт это и повторяет прогон.
- Прогон `run-talos.ps1` — ~77 с, из них 30 с замер; интро скрипт игры уже
  пропускает.
- Профилированные прогоны (`HASVK_WDDM_PROFILE_PASSES`) медленнее на 10–15 %;
  FPS сравнивать только без профиля.
- Микротесты GPU короче ~1 с идут на холодной частоте (440–600 МГц против
  ~1 ГГц): сравнивать по длительной нагрузке (250+ запусков).
- Стенд записи команд: `replay_pass_probe` с `REPLAY_RECORD_ONLY=<n>` (разброс
  ~1 %); горячие строки — `rip_sampler` с `RIP_LINES=<n>`.
- CTS и Talos одновременно не запускать. `build-icd.ps1` — только когда CTS
  не держит `build\icd`; `run-cts.ps1` всегда берёт DLL оттуда.
- После каждого изменения: `test-all`; для синхронизации, глубины и конвейера
  — выборки CTS по затронутым группам.
