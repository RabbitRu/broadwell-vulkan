# Производительность: Vulkan против DX11 на Iris 6100

Документ этапа 7 (`docs/roadmap.md`): сделать Vulkan быстрее DX11 в The Talos
Principle. Допустимы только универсальные исправления драйвера, без профилей
под отдельные игры (решение пользователя). Этап измерен до конца (раздел 0):
в Talos цель универсальными исправлениями драйвера не достигается; методика и
инструменты отсюда переносятся на следующую игру — Dota 2 (roadmap, этап 8).

Содержание: итог (раздел 0), измерения (1; повторный разбор журналов — 1.9),
что изменено в драйвере (2),
гипотезы и их статус (3), проверенное и отклонённое (4), **как повторить
каждое измерение** (5), методика и подводные камни (6), сбой системы
2026-11-20 и меры безопасности (7). Все оптимизации этапа с цифрами —
roadmap, раздел 1.8; инструменты — там же, раздел 1.7.

Состояние на 2026-11-20. Метки вида 2.1–2.10 — прежние номера тем этого
документа; на них ссылаются roadmap и комментарии в коде.

## 0. Итог

- **Где сейчас:** в сериях 2026-11-20 Vulkan 70–83 FPS (чаще 75–79), DX11
  79–87 FPS; отношение 0,87–0,96 в парах прогонов (раньше записано 79–83 против
  83–91 — машина с тех пор работает горячее; сравнивать только прогоны одной
  серии). 1 % худших кадров: Vulkan 24–35 FPS, DX11 30–40.
- **Кадр под обоими API задаёт главный поток игры** (87–90 % времени занят).
  Наш драйвер обходится ему дешевле, чем драйвер Intel DX11 вместе с рантаймом
  D3D11 (≈2,0 против ≈3,4 мс на кадр), а собственный код игры под Vulkan идёт
  медленнее (≈8,6 против ≈6,3 мс).
- **Причина — общий бюджет питания CPU и GPU.** Путь Vulkan игры строит тени
  заново каждый кадр (3,7 млн вызовов FS на карту против 7 тыс. у DX11), GPU
  занят 81–91 % времени против 73–77 %, и CPU работает на 4–19 % более низкой
  частоте. Прямая проверка: измерительное снятие FS альфа-теста в тенях подняло
  частоту CPU на 18–25 % и FPS на 15 %.
- **На одинаковой работе драйвер вровень с драйвером Intel** или быстрее:
  заливка глубины с альфа-тестом, мелкие проходы пост-обработки, основной
  проход и предпроход, выборки texel-буфера в VS.
- **Проверены все гипотезы с заметным ожиданием** (раздел 3). Осталось две
  дорогих с низким ожиданием (C5, C6). Обогнать DX11 в Talos универсальными
  исправлениями драйвера, по этим измерениям, скорее всего нельзя: отставание
  задаёт путь Vulkan самой игры, а убрать его можно только профилем под игру.
- **Повторный разбор сохранённых журналов (раздел 1.9)** уточнил картину:
  по собственной разбивке игры ~90 % разрыва сидит в секциях shadows (+0,8 мс)
  и misc (+0,4 мс) главного потока, секция scene совпадает; вызов ядра для
  вывода кадра в 27–40 % кадров длится 9–11 мс (ядро держит его, пока GPU не
  закончит прошлый кадр), и в этих же кадрах главный поток ждёт
  `vkGetQueryPoolResults` 0,7–1,0 мс — но кадры от этого не длиннее. Не
  выяснено, чего главный поток ждёт остальные ~1,6 мс на кадр и что делают
  потоки игры, которые под Vulkan тратят на ~26 % логического CPU больше
  (гипотезы группы E, раздел 3).
- **Замер потоков и кода под обоими API (раздел 1.10)** ответил на оба
  вопроса. Главный поток ждёт ответа Steam (под обоими API). Лишний CPU —
  поток `VLKSupportThread` самой игры с циклом без ожидания (~20 %
  логического CPU) и наш поток очереди (8 %). На главном потоке драйвер с
  вызовами ядра дешевле драйвера Intel на ~1,0 мс на кадр (2,35 против 3,37),
  а код самой игры идёт на 2,27 мс дольше (8,46 против 6,19): путь Vulkan
  игры дороже её пути DX11, и общий код замедлен в 1,27 раза. Паритет
  требует −1,75 мс при 2,15 мс драйвера на кадр: универсальными
  исправлениями драйвера он не достигается; ускорение записи команд сделано
  (−5 % на стенде записи draw, в игре в пределах разброса; раздел 3, «B2,
  повторно»).
- **Тени (2026-11-20).** Обход PMA проверен в обратную сторону: без него 42
  FPS против 78, то есть ранний тест глубины для шейдеров с `discard` уже
  даёт почти двукратный выигрыш, и весь он в тенях: обход снимает задержки
  конвейера, число вызовов FS от него не зависит. Две карты теней стоят
  4,2–6,0 мс на кадр против 2,4 мс у DX11; разница — пиксельная работа,
  которую заказывает путь Vulkan игры. Оставшиеся идеи малы (раздел 3,
  «Тени: что осталось»): правило C1 повторно теперь оценивается в 0,2–0,4 мс
  и риска не стоит.

## 1. Измерения

Встроенный бенчмарк Talos (`tools/run-talos.ps1`: Demo, 30 с, 640×480,
одинаковые авто-настройки). Как снято каждое число — раздел 5.

### 1.1 FPS и загрузка GPU

| | DX11 (драйвер Intel) | Vulkan (HasVK/WDDM) |
|---|---|---|
| Средний FPS, серии 2026-11-20 | 79,1–87,2 | 69,7–83,0 |
| 1 % худших кадров | 30–40 FPS | 24–35 FPS |
| GPU 3D занят (счётчик Windows) | 73–77 % | 81–91 % |
| Работа GPU на кадр | ≈8,6 мс | ≈10,8–11,0 мс (метки GPU в журнале) |

В начале этапа Vulkan давал 27,8 FPS (roadmap 1.8).

### 1.2 Как проходит кадр под Vulkan (журнал `HASVK_WDDM_TIMELINE`, тёплые прогоны)

| | Значение |
|---|---|
| Кадр | 12,2–12,5 мс (77,6–80,3 FPS в окне замера) |
| GPU занят по своим меткам | 10,8–11,0 мс (85–87 %) |
| GPU простаивает | 1,7–1,9 мс: из них 1,3–1,6 мс игра ещё не отправила работу (её поток в своём коде), ~0,34 мс — от вызова ядра до старта GPU |
| Главный поток игры, CPU | 10,9–11,2 мс на кадр (87 % времени) |
| Главный поток в блокирующих вызовах драйвера | ~0,45 мс на кадр, из них `vkGetQueryPoolResults` 0,28 мс (22 вызова), `vkWaitForFences` 0,01 мс |
| Отправок в ядро на кадр | 3,6 (одна — вывод кадра) |
| Отправок «в полёте» при вызове `vkQueuePresentKHR` | чаще всего 1 |

Игра не ждёт GPU (`vkWaitForFences` почти ноль), поэтому задержка сигнала о
завершении (поток завершения просыпается через ~0,5–0,7 мс после конца работы
GPU) на кадр не влияет.

### 1.3 Главный поток: DX11 против Vulkan

Время CPU потоков — по счётчику циклов (`QueryThreadCycleTime`), в окне замера:

| | DX11 | Vulkan |
|---|---|---|
| FPS прогона | 86,3 | 78,5 |
| Главный поток игры | 89,9 % (10,4 мс на кадр) | 86,9 % (11,1 мс на кадр) |
| Все потоки процесса | 135 % одного логического CPU | 167–173 % |
| Наши служебные потоки | — | поток очереди 8,1 % (1,0 мс на кадр), поток завершения 1,5 % (0,18 мс) |

Сэмплы стеков главного потока (`rip_sampler`, 20 с):

| Доля выборок | DX11 (81 FPS) | Vulkan (66 FPS под сэмплером) |
|---|---|---|
| Драйвер: `igd10iumd64` + D3D11 / `vulkan_hasvk_wddm` | ~29 % (≈3,4 мс на кадр) | 15,7 % (≈2,0 мс) |
| Собственный код игры | ~55 % (≈6,3 мс) | ~68 % (≈8,6 мс) |
| Ожидание (`NtWaitForSingleObject`) | 6,9 % | 8,9 % |

Драйвер в главном потоке под Vulkan — запись команд: `gfx8_CmdDrawIndexed`
(10 % выборок вместе с вложенными функциями), `anv_CmdBindPipeline` (1,5 %),
начало прохода, привязка буферов вершин.

### 1.4 Частота CPU и бюджет питания

i5-5257U (2 ядра, 4 потока, 2,7 ГГц) и Iris 6100 делят бюджет питания. Счётчики
`\Processor Information(_Total)` в окне замера, прогоны вперемешку:

| Пара | DX11: частота / предел / GPU / FPS | Vulkan: частота / предел / GPU / FPS |
|---|---|---|
| 1 | 2215 МГц / 84 % / 73 % / 79,7 | 1981 МГц / 74 % / 86 % / 74,2 |
| 2 | 2527 МГц / 94 % / 77 % / 86,5 | 2434 МГц / 89 % / 91 % / 83,0 |
| 3 | 2379 МГц / 88 % / 76 % / 84,3 | 1923 МГц / 74 % / 81 % / 72,9 |

«Предел» — `% Performance Limit`; флаги ограничения в обоих API — 0x2.

Прямая проверка связи «работа GPU → частота CPU»: измерительный
`HASVK_WDDM_SHADOW_NO_DISCARD=1` (снимает FS альфа-теста в проходах только
глубины, меняет картинку, не исправление) вперемешку с базой:

| | База | Без FS альфа-теста в тенях |
|---|---|---|
| Прогоны 1–2 | 66,4 FPS, CPU 1629 МГц, GPU 82 % | 77,5 FPS, CPU 1918 МГц, GPU 73 % |
| Прогоны 3–4 | 72,8 FPS, CPU 1878 МГц, GPU 84 % | 84,2 FPS, CPU 2350 МГц, GPU 76 % |

Вывод: кадр формально упирается в CPU, но любая экономия энергии GPU (и CPU в
служебных потоках) поднимает частоту главного потока игры.

### 1.5 Время GPU по проходам

| Проход | DX11, мс | Vulkan, мс |
|---|---|---|
| 2 карты теней 1536² (D16) | 2,4 | ~5,2 |
| Основной 640×480 (RGBA16F + D32) | 3,5 | ~2,9 |
| Предпроход (R16F + D32) | 1,7 | ~1,1 |
| Пост-обработка, копии | ~1 | ~1,5 (из них ~0,3 — три прохода в изображения цепочки по разу в три кадра, ~0,15 — копии буферов) |

Столбец DX11 — прокси `d3d11.dll`, Vulkan — профиль проходов. Мелкие проходы по
отдельности вровень: 64×64 — 0,24–0,29 мс против 0,38, 640×480 — 0,21 против
0,19–0,21, 320×240 — 0,18 против 0,18, цепочка 160×120 … 1×1 вровень.

Тени, статистика конвейера на одну карту:

| | DX11 | Vulkan |
|---|---|---|
| Вершин на входе | 384 тыс. | 429 тыс. |
| Вызовов VS | 161 тыс. | 181 тыс. |
| Вызовов PS/FS | 7 тыс. | 3 747 тыс. |

Путь DX11 игры не очищает карты теней и переиспользует их между кадрами (draw
почти целиком отбрасываются ранним тестом глубины), путь Vulkan каждый проход
очищает карту и строит её заново с альфа-тестом. Настройка игры
`vlk_iEmulateAlphaTest 0` число вызовов не меняет.

| Тест | Vulkan | D3D11 Intel | Отношение |
|---|---|---|---|
| VS: 4 итерации × 3 `texelFetch` (как листва Talos) | 487 Мверш/с | 487 Мверш/с | 1,00 |
| Пустой VS (фиксированный путь вершин) | 948 Мверш/с | 1063 Мверш/с | 0,89 |
| 1000 draw по 3 вершины без смены состояния | 0,11 мкс/draw | 0,08 мкс/draw | — |
| Сэмплер при прогретой частоте GPU | 18,8 Гвыб/с | 19,8 Гвыб/с | 0,95 |
| Цикл FMA, 250 запусков | 442 GFLOPS | 525 GFLOPS | 0,84 |
| 8 слоёв D16 1536² с `discard`, спереди назад, с быстрой очисткой HiZ | 1,58–1,60 мс | 1,51–1,55 мс | 0,96 |
| То же сзади вперёд | 5,19–5,30 мс | 5,16–5,54 мс | 1,0 |
| 8 слоёв без FS, сзади вперёд | 0,41–0,60 мс | 0,36–0,43 мс | 0,7–0,9 |

`depth_fill_probe` очищает глубину в 1.0, а для читаемой глубины быстрая
очистка HiZ у нас — только значением 0.0 (Talos очищает в 0.0 и её получает).
Без быстрой очистки первый слой с `discard` медленнее: 2,11 мс вместо 1,58.

### 1.8 Медленные кадры (1 % худших)

- Почти все медленные кадры (6–8 за 26 с, 40–90 мс) — заминки **ровно раз в
  ~5 с**: главный поток игры 40–70 мс вне CPU и вне вызовов драйвера. Они есть
  и под DX11 (таблица кадров игры, прогон DX11 `BenchFrames_0217`: 4,43 / 9,44 /
  14,44 / 19,46 / 24,50 / 29,51 с по 51–63 мс) — это поведение игры или системы.
- Файлы кэша шейдеров на 1 % худших не влияют: с ними 30,2 / 30,6 FPS, без них
  (`HASVK_WDDM_INTERNAL_CACHE=0`) 30,5 / 29,7.
- Найдено и исправлено (раздел 2): пока поток подгрузки игры выделял память
  (`vkAllocateMemory` 10–40 мс в ядре), главный поток стоял в `vkGetFenceStatus`
  (до 13 мс), `vkWaitForFences` и `vkQueuePresentKHR` (~10 мс). На 1 % худших
  Talos правка не видна (26,7–32,7 FPS против 25–33): их задают заминки игры.
- Остаётся: отправка вывода в ядро растягивается на время выделения памяти
  другим потоком (вызов ядра до 35 мс при выделении 41 мс) — блокировка внутри
  ядра Windows.

### 1.9 Повторный разбор сохранённых журналов (2026-11-20)

Новых прогонов нет: разобраны файлы в `build\talos` (журналы кадра `tl-2`,
`tl-3`, `af-tl-1`, `af-tl-2`, выводы 87 тёплых прогонов, замер окна
`sample-check`).

**Секции кадра по счёту самой игры.** Бенчмарк печатает
`Sections: AI=…%, physics=…%, sound=…%, scene=…%, shadows=…%, misc=…%`;
проценты, умноженные на длину кадра, дают миллисекунды главного потока
(`tools/talos-sections.py`). Тёплые прогоны с вечера 2026-11-19:

| Секция, мс на кадр | DX11 (7 прогонов) | Vulkan (80) | Разница |
|---|---|---|---|
| AI | 1,48 | 1,53 | +0,05 |
| physics | 0,39 | 0,39 | +0,01 |
| sound | 0,22 | 0,26 | +0,04 |
| scene | 6,04 | 6,02 | −0,02 |
| shadows | 2,00 | 2,78 | +0,78 |
| misc | 1,61 | 2,03 | +0,42 |
| Кадр | 11,75 | 13,02 | +1,27 |

По 11 прогонам вперемешку (6 DX11, 5 Vulkan): shadows +0,89, misc +0,56,
scene +0,21, AI +0,12 при разнице кадра +1,91 мс. Игра округляет до целого
процента (±0,07 мс на строку в одном прогоне); что именно входит в секцию и
считает ли она ожидания, неизвестно.

Что из этого следует и что нет:
- Пониженная частота CPU (1.4) замедлила бы все секции на 4–19 %. AI, physics
  и scene почти совпадают, а shadows длиннее на 39 %. Значит, одной частотой
  разрыв не описывается — либо scene под Vulkan сама по себе дешевле (драйвер
  обходится главному потоку дешевле, 1.3) и частота это съедает.
- Секция shadows: в снимке прохода теней 176 draw, очистка при входе
  (`load 1`). При ~1 мкс на draw запись двух-трёх проходов драйвером — 0,35–0,7
  мс из 2,78; чем занято остальное и почему на 0,8 мс больше, чем под DX11, не
  измерено.
- Опыт без FS альфа-теста в тенях (1.4) по секциям: scene 6,32 → 5,11 мс,
  shadows 2,88 → 2,49, misc 2,20 → 2,02, AI 1,65 → 1,66. Снятие работы GPU в
  тенях сократило секцию scene на 1,2 мс, а AI не изменилась, хотя частота CPU
  выросла на 25 %. Либо AI упирается в память, а не в частоту, либо в scene
  главный поток чего-то ждёт; одна пара прогонов этого не решает.

**Вызов ядра для вывода кадра** (новый раздел отчёта `timeline-report.py`,
четыре журнала):

| | Короткие вызовы | Длинные вызовы |
|---|---|---|
| Доля | 60–73 % | 27–40 % |
| Длительность | медиана 1,44–1,60 мс | в среднем 9,1–9,6 мс |
| Незавершённых отправок перед ним на GPU при входе / при возврате | 2 / 1 | 4 / 1 |
| Возврат относительно сигнала о завершении более ранней отправки | 15 мкс | 32 мкс |
| Копия кадра стартует на GPU после возврата через | 8,7–9,3 мс | 11,1–11,3 мс |
| `vkQueueSubmit` игры, принятых за время вызова | 0 | 1,6–1,9 на вызов; суммарно они ждут 2,5–3,2 мс на кадр |
| Простой GPU после копии кадра | медиана 1,2–2,0 мс (1,1–1,5 мс на кадр) | 0,25 мс (0,11–0,14 мс на кадр) |
| Кадр игры во время вызова | 12,5–13,2 мс, CPU 10,9–11,4 | 12,4–12,7 мс, CPU 10,9–11,1 |
| Из него в `vkGetQueryPoolResults` | 0,01 мс | 0,7–1,06 мс |

- Вызов возвращается ровно по завершении более ранней отправки, когда перед
  выводом остаётся одна незавершённая (большая отправка этого же кадра), то
  есть когда GPU закончил прошлый кадр. К частоте экрана возвраты не привязаны
  (сила привязки фазы 0,04–0,08 при 1 для полной). Остальные вызовы ядра —
  0,05 мс, максимум 0,7.
- Кадры идут в двух режимах: в 60–73 % GPU догнал игру и простаивает 1,2–2 мс,
  пока она не отправит работу; в 27–40 % GPU отстаёт на кадр, вывод стоит в
  ядре, отправки следующего кадра ждут в потоке очереди.
- Все долгие ожидания `vkGetQueryPoolResults` главного потока (в 18 % кадров
  по 0,5–3,5 мс, 0,27–0,30 мс на кадр) приходятся на кадры с длинным вызовом
  вывода (405 из 406 и 464 из 466). Ожидание кончается раньше возврата вызова:
  игра ждёт запрос из уже отправленной работы, до которой GPU ещё не дошёл.
- **Кадры от этого не длиннее.** Кадр с длинным вызовом — 12,4–12,7 мс, с
  коротким — 12,5–13,2 мс; время главного потока вне CPU в обоих случаях

### Тени: что осталось (2026-11-20)

Исходные числа: две карты теней стоят GPU ~5,2 мс под Vulkan против 2,4 мс
под DX11 (1.5), и это не скорость драйвера, а объём работы: путь Vulkan игры
очищает карту и строит её заново каждый кадр (3,7 млн вызовов FS с
альфа-тестом на карту), путь DX11 карту не очищает, и почти все draw
отбрасывает ранний тест глубины (7 тыс. вызовов). Тот же draw листвы драйвер
Intel выполняет не быстрее (1.6). Снять эту работу драйвер не вправе: очистку
и перестроение заказывает игра. Поэтому «тени как у DX11» универсальной
правкой не получить; остаётся удешевлять то же самое и экономить в других
проходах — бюджет питания у CPU и GPU общий (1.4).

  удешевление самого переключения уже пробовали (№ 4).

### Подробности проверок

**A1–A3, A6, B1 (журнал кадра и потоки).** Журнал `HASVK_WDDM_TIMELINE` в трёх
тёплых прогонах Talos, разбор `tools/timeline-report.py` (раздел 5.3); контроль
DX11 — время CPU потоков через `run-talos.ps1 -Sample` и сэмплы стеков
`-RipModule igd10iumd64.dll`. GPU простаивает, пока главный поток игры в своём
коде; поток очереди в простоях GPU не виноват (0,00 мс в разбивке простоев).

**A2 (бюджет питания).** Счётчики частоты в трёх парах прогонов DX11/Vulkan и
опыт с `HASVK_WDDM_SHADOW_NO_DISCARD=1` в двух парах (1.4).

**B2.** `rip_sampler` на стенде `REPLAY_RECORD_ONLY` (60 000 записей снятого
прохода теней) с `RIP_LINES=25`: `vk_dynamic_graphics_state_copy` 7,9 % выборок,
`gfx8_CmdDrawIndexed` 8,9 %, `emit_binding_table` 5,9 %,
`cmd_buffer_flush_push_constants` 4,7 %, `gfx8_cmd_buffer_flush_dynamic_state`
4,7 %. Копирование динамического состояния вызывается на каждую привязку
конвейера, а в стенде привязки идут только при смене конвейера, поэтому
пропуск повторных привязок не поможет; экономить можно только на сменах между
конвейерами с одинаковым статическим состоянием (классы эквивалентности при
создании конвейера плюс счётчик изменений состояния командного буфера в среде
Mesa) — ~0,16 мс из ~2 мс драйвера на кадр при риске тихо неверного состояния.

**B2, повторно (после 1.10).** Стенд `REPLAY_RECORD_ONLY`: 984–993 нс на draw,
из них драйвер ~650 нс (остальное — сам стенд). По точкам входа:
`vkCmdDrawIndexed` 66 % времени драйвера, `vkCmdBindPipeline` 13 %,
`vkCmdBindVertexBuffers` 7 %. Проверено, можно ли пропускать повторное
применение статического состояния конвейера: в проходе 176 draw, 14 конвейеров,
111 смен конвейера, и ни одна не ведёт к конвейеру с тем же записанным
состоянием (различаются вершинные форматы и раскладки) — пропускать нечего.
Остаются локальные ускорения: заполнение состояния поверхности для
динамического UBO по шаблону (~6 % времени драйвера на draw) и адреса буферов
вершин без обращения к объектам BO (~3 %). Вместе ~0,15 мс на кадр, около 1 %
FPS Talos — в игре неизмеримо; оценка «0,4–0,6 мс» из первого плана не
подтвердилась.

Первое сделано 2026-11-20: состояние поверхности динамического uniform- или
storage-буфера берётся из шаблона устройства, в нём меняются только число
элементов и адрес (`anv_wddm_fill_dynamic_buffer_surface_state`). При создании
устройства шаблон сверяется с выводом ISL на 240 сочетаниях типа, размера и
адреса; при любом расхождении остаётся путь ISL (так была поймана ошибка
первой версии: состояние Gen8 — 16 слов, а не 13). Стенд: 931–941 нс на draw
против 981–997 (−5 %, четыре прогона против трёх). Talos: 74,6 и 77,8 FPS
(середина 98 %) — в обычном разбросе, выигрыш в игре не виден, как и
ожидалось. CTS по динамическим буферам (`binding_model.dynamic_offset`,
`shader_access.*buffer_dynamic*`, выборки `descriptorset_random`, `ubo`,
`ssbo`, `push_descriptor`): 11 118 Pass, 0 Fail.

Второе (адреса буферов вершин) не делалось: путь уже встроенный, остаётся
одно обращение к строке кэша BO и отметка зависимости буфера; ожидаемые ~2 %
стенда не стоят риска для учёта зависимостей.

**B3.** Вся Mesa с `/clang:-march=broadwell`: стенд `REPLAY_RECORD_ONLY` —
987–997 нс на draw против 987–990 у базы (три чередования). LTO:
`meson.build` Mesa останавливает сборку («Building Mesa with LTO is not
supported»), запрет не обходили.

**B3, повторно (2026-11-20): компилятор.** Стенд `REPLAY_RECORD_ONLY`, сборки
чередуются:
- `-O3` вместо `-O2` (clang 19): 929–937 против 928–940 нс — без выигрыша, не
  включали.
- PGO (clang 19, `-fprofile-instr-generate`, профиль стенда и прогона Talos,
  `llvm-profdata merge`): инструментированная сборка и профиль получены, сборка
  с профилем не доведена — опыт остановлен ради перехода на clang 23. Заметки:
  `-fprofile-instr-use=` требует абсолютного пути без кириллицы (иначе ломаются
  проверки конфигурации meson), библиотеку `clang_rt.profile` clang-cl ищет в
  `lib\clang\<версия>\lib\windows` своего дистрибутива.
- **clang 23.1.6 с `-march=broadwell`** против clang 19.1.5 без него, четыре
  чередования: **906, 922, 908, 906 против 964, 931, 937, 947 нс** на draw
  (−3 %). Поскольку `-march` на clang 19 выигрыша не давал (выше), выигрыш
  в основном от нового компилятора. В коде появились FMA и в ~9 раз больше
  операций с `ymm`. Talos (прогрев каждой сборки, затем чередование):
  clang 19 — 77,0 / 78,8 / 77,3 / 77,9 FPS, clang 23 — 76,1 / 76,5 / 80,1
  (ещё один прогон clang 23 оборвался через 2 с — бот игры закончил уровень, не
  учтён): в пределах разброса, как и ожидалось — 3 % от ~2 мс драйвера на кадр
  это ~0,06 мс главного потока. Оставлено как сборка по умолчанию.
  Проверка сборки: `test-all` — все 22 проверки; 90 тестов CTS, не проходивших
  в полном прогоне, — 89 Pass и ожидаемый `conformance_version`; равномерная
  выборка всего CTS (каждый 40-й тест, 71 896 тестов) — 17 442 Pass,
  1 QualityWarning, 0 Fail, остальное NotSupported.

Переход на clang 23 потребовал одной правки порта: clang 23 проверяет
`-Wpadded` и для раскладки Microsoft ABI, а ключи программ ELK
(`elk_base_prog_key`, `elk_vs/tcs/tes/fs_prog_key`) рассчитаны на правила
битовых полей System V — в Microsoft ABI новый блок битовых полей начинается
при смене размера типа, и в ключах остаются дыры. Раскладка та же, что и у
clang 19 (ABI один), просто clang 19 её не проверял. Дыры безвредны: все ключи,
которые хэшируются и сравниваются `memcmp`, обнуляются `memset`
(`populate_*_prog_key` в `anv_pipeline.c`, ключи BLORP), поэтому под Windows
`-Wpadded` в `elk_compiler.h` больше не ошибка. Заодно исправлен `%u` для
`uint64_t` в сообщении о нехватке памяти пула (`anv_allocator.c`).

**C1.** Правило: при уже включённом обходе PMA не выключать его перед draw,
который запускает FS без `early_fragment_tests`. Первый же прогон Talos с этой
сборкой (холодный, с профилем проходов) закончился критической ошибкой Windows
0x119. Правило удалено; без основания в PRM не повторять.

**C2.** `depth_fill_probe` против `d3d11_depth_fill_probe`, 400 повторов, 8 слоёв,
оба порядка, два раунда; затем то же с `HASVK_WDDM_NO_HIZ_SAMPLING=1`, чтобы
получить быструю очистку при очистке в 1.0 (1.6).

**C3.** Профиль проходов `HASVK_WDDM_PROFILE_PASSES=1` против разбивки прокси
`d3d11.dll` по целям рендеринга (1.5).

**C4.** `INTEL_DEBUG=no8` (FS только SIMD16, где он собирается) против базы,
по холодному и тёплому прогону на вариант, два раунда в обратном порядке.
Раньше эту проверку портил постоянный UUID кэша; теперь каждый вариант
компилируется под свой UUID.

**D1, D2.** Чередование с `HASVK_WDDM_INTERNAL_CACHE=0`; медленные кадры —
`timeline-report.py --slow-detail` и `tools/bench-frames.py` по таблицам кадров
игры обоих API.

## 5. Как повторить каждое измерение

Все команды — из корня проекта в PowerShell; Steam должен быть запущен (без него
Talos падает в `ntdll` до создания журнала).

### 5.1 Сборка

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\build-icd.ps1      # драйвер в build\icd
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\build-probes.ps1   # пробы и rip_sampler в build\probes
```

После каждой пересборки драйвера первый прогон Talos холодный (раздел 6).

### 5.2 Бенчмарк Talos

```powershell
.\tools\run-talos.ps1 -Api Vulkan -Tag v1                    # FPS и 1 % худших
.\tools\run-talos.ps1 -Api Direct3D11 -Tag d1                # то же под DX11
.\tools\run-talos.ps1 -Tag s1 -Sample                        # + потоки, частота CPU, GPU, DWM в окне замера
.\tools\run-talos.ps1 -Tag r1 -RipModule vulkan_hasvk_wddm.dll                 # + стеки (20–24 с)
.\tools\run-talos.ps1 -Api Direct3D11 -Tag r2 -RipModule igd10iumd64.dll       # стеки под DX11
.\tools\run-talos.ps1 -Tag e1 -Env 'HASVK_WDDM_INTERNAL_CACHE=0'               # переменные окружения игре
.\tools\run-talos.ps1 -Api Direct3D11 -Tag p1 -D3D11Proxy build\probes\d3d11-proxy\d3d11.dll  # разбивка кадра DX11
```

Результаты — в `build\talos\<Tag>.*`: вывод (`.stdout.txt`), журнал игры
(`.Talos.log`), замер окна (`.sample.txt`, `.rip.txt`), профиль прокси
(`.d3d11-profile.txt`). Прогон ~77 с, замер — 30 с из них. `-Sample` и
`-RipModule` запускают `tools/talos-window.ps1` отдельным процессом; он ждёт
строку «Starting automated benchmark» этого прогона и мерит с +3 по +27 с.

### 5.3 Журнал кадра

```powershell
$csv = "$PWD\build\talos\tl.timeline.csv"
.\tools\run-talos.ps1 -Tag tl -Env "HASVK_WDDM_TIMELINE=$csv"
.\.tools\python\python.exe -I tools\timeline-report.py $csv --talos-log build\talos\tl.Talos.log
.\.tools\python\python.exe -I tools\timeline-report.py $csv --talos-log build\talos\tl.Talos.log --slow-detail
```

Отчёт: FPS и время кадра в окне замера (по журналу игры, +2…+28 с от начала
бенчмарка), занятость GPU по его собственным меткам, простои GPU с разбивкой
(поток очереди занят, ждёт семафор, ещё нет `vkQueueSubmit` — и что в это
время делал поток игры, от вызова ядра до старта GPU), CPU главного потока и
его время в каждом блокирующем вызове, время вызовов ядра (вывод отдельно),
задержки пробуждения потока завершения, медленные кадры. `--slow-detail`
перечисляет всё дольше 1 мс на всех потоках в каждом медленном кадре.

Формат CSV: `ns,type,thread,a,b`; `ns` — `QueryPerformanceCounter` в
наносекундах. Типы (`enum anv_wddm_timeline_type` в `mesa/anv_wddm.h`): начало
и конец вызова (a — какой вызов), вход в `submit()`, конец ожиданий семафоров,
начало и конец вызова ядра (a — серийный номер, b — признак вывода или циклы
потока), пробуждение потока завершения (b — метки GPU начала и конца, тики
12,5 МГц), сигнал, калибровка (rdtsc и местное время). Метки GPU переводятся в
часы CPU по нижней огибающей «пробуждение минус конец работы» (разброс
оценки — 0,1–0,5 мс). Журнал не сериализует GPU, в отличие от профиля проходов.

### 5.4 Профиль проходов GPU

```powershell
.\tools\run-talos.ps1 -Tag prof -Env 'HASVK_WDDM_PROFILE_PASSES=1'
```

Каждые 5 с в `build\talos\prof.stdout.txt`: время GPU на кадр по проходам
(размер, форматы, HiZ, число draw, переключения отбрасывающих конвейеров),
статистика конвейера, конвейеры только глубины, запросы сбросов и остановок по
причинам, время ядра на отправки, выделения памяти. `HASVK_WDDM_PROFILE_DRAWS=1`
добавляет время каждого draw. Профиль медленнее на 10–15 %: FPS по нему не
сравнивать.

```powershell
# стеки: чего ждут потоки и кто вызывает ядро (игра под сэмплером медленнее на 8–12 %)
.\tools\run-talos.ps1 -Api Vulkan -Tag vk-rip -RipModule vulkan_hasvk_wddm.dll
.\tools\run-talos.ps1 -Api Direct3D11 -Tag dx-rip -RipModule igd10iumd64.dll
# адреса кода без обхода стеков (игру не замедляет), затем сравнение в мс на кадр
$env:RIP_NOWALK = '1'; $env:RIP_RVAS = '400'
.\tools\run-talos.ps1 -Api Vulkan -Tag vk-rva -RipModule vulkan_hasvk_wddm.dll
.\tools\run-talos.ps1 -Api Direct3D11 -Tag dx-rva -RipModule igd10iumd64.dll
.\.tools\python\python.exe -I tools\rip-compare.py build\talos\dx-rva.rip.txt <FPS DX11> build\talos\vk-rva.rip.txt <FPS Vulkan>
```

`-Sample` теперь печатает также время ядра, DPC и прерываний и CPU других
процессов. `rip_sampler` считает CPU потоков по счётчику циклов, печатает
доли выборок по модулям, а выборки внутри системных DLL — по вызывающему
(три первых кадра вне `ntdll`/`kernelbase`/`kernel32`/`win32u`/`gdi32`:
`модуль!функция` при наличии PDB, иначе `модуль+смещение`). Потоки с
загрузкой ниже 1 % он сэмплирует только первые полсекунды. `rip-compare.py`
сопоставляет два вывода: потоки, модули главного потока и страницы кода
(4 КиБ) в миллисекундах кадра, код «только в одном прогоне» и медианное
замедление общего кода. Имя потока игры по его номеру — строки
`Created thread <hex>(<имя>)` в `Talos.log`.

## 6. Методика и подводные камни

- Разброс FPS Talos ±5 %, а между сериями — больше (машина нагревается за
  серию и за день): сравнивать только чередованием в одной серии, не меньше
  двух-трёх пар.
- Первый прогон после новой сборки холодный: игра перекомпилирует все
  конвейеры (1 % худших ~8,7 FPS). Его не учитывать.
- Изменения генерации кода — только с разными UUID (5.8).
- Тестовый бот игры иногда завершает уровень через ~2 с; `run-talos.ps1`
  повторяет такой прогон (с `-NoRetry` — нет). Замер окна при этом
  перезапускается вместе с прогоном.
- Время CPU потоков — только `QueryThreadCycleTime`: `TotalProcessorTime`
  (`GetThreadTimes`) обновляется по тикам таймера и показывал главный поток
  Vulkan на 26 % вместо 87 %.
- Счётчики PDH (`Get-Counter`) по английским именам не находятся в процессе с
  русским языком интерфейса (`Start-Process`, `Start-Job`): нужен
  `SetThreadUILanguage(0x409)` (так сделано в `talos-window.ps1`). В фоновых
  заданиях PowerShell (`Start-Job`) счётчиков процессора нет вовсе.
- Профиль проходов медленнее на 10–15 %, `rip_sampler` — сильнее (66 FPS
  вместо ~78): доли выборок сравнимы, абсолютные FPS — нет.
- Микротесты GPU короче ~1 с идут на холодной частоте (440–600 МГц против
  ~1 ГГц).
- CTS и Talos одновременно не запускать; `build-icd.ps1` — только когда CTS не
  держит `build\icd`.
- После каждого изменения: `test-all`; для синхронизации, глубины, памяти и
  конвейера — выборки CTS по затронутым группам; для изменений, которые меняют
  поведение GPU, — помнить о разделе 7.

## 7. Сбой системы 2026-11-20 и меры безопасности

- Первый прогон Talos со сборкой правила C1 (обход PMA) закончился критической
  ошибкой Windows **0x119 VIDEO_SCHEDULER_INTERNAL_ERROR** (параметры 0xA,
  0xC2BED4, 0xC2BED7) и перезагрузкой. Значение параметров не сверено с
  документацией (сайт был недоступен); 2 и 3 похожи на номера fence. Других
  таких сбоев за 60 дней нет; ~20 прогонов перед этим прошли без сбоев.
- После перезагрузки в 2 из 4 прогонов `test-all` GPU зависал на прямом пути
  транспорта без ICD (`test-spirv`, состояние устройства 3 — HUNG). При загрузке
  Windows записала «встроенный контроллер (EC) не ответил вовремя». После
  паузы три `test-all` подряд и все дальнейшие прогоны прошли без зависаний.
- Второй сбой, 2026-11-20 13:38: критическая ошибка **0xD1** через минуту
  после зависания видеодвижка (отчёт Windows LiveKernelEvent 141) на тесте CTS
  со сбросом регистров шейдера. Это уточняет картину и первого сбоя: в час
  ошибки 0x119 Windows тоже записала два отчёта 141. Систему роняет не само
  изменение драйвера, а зависание видеодвижка, после сброса которого драйвер
  ядра Intel иногда падает (около 50 зависаний за время работы, два сбоя).
  Главная причина зависаний — шейдеры со сбросом регистров без буфера сброса
  — исправлена (`docs/cts-expected-failures.md`). Число отчётов 141 до и после
  прогона — в папках `Kernel_141_*` каталогов
  `C:\ProgramData\Microsoft\Windows\WER\ReportQueue` и `ReportArchive`.
- Вторая причина зависаний в CTS найдена и исправлена 2026-11-20: шейдеры с
  режимом `DepthUnchanged` (знаковое битовое поле-перечисление,
  `docs/cts-expected-failures.md`). Разбор стоил около 20 сбросов
  видеодвижка, сбоев системы не было. После этой серии один раз завис родной
  пробник транспорта в `test-all` (`generated-compute`, 16:25) — как и после
  первого сбоя, без участия ICD; повтор `test-all` прошёл.
- Приём для разбора зависаний: перед каждой отрисовкой и операцией BLORP
  выдавать `PIPE_CONTROL` с остановкой командного потока и записью номера шага
  в память командного буфера; после потери устройства последний записанный
  номер показывает шаг, который не завершился. Код отметок временный, в
  сборке его нет (вставлялся через `mesa/graphics_sources.py`).
- Меры: изменения, которые меняют состояние GPU сверх того, что требует PRM,
  не делать без основания в PRM; опыты, вешающие GPU (DeviceLost в CTS,
  `INTEL_DEBUG=spill_fs` на 64-битных операциях подгрупп), не повторять без
  согласия пользователя; после сбоя — сначала несколько `test-all`, потом
  нагрузка; Talos.ini и папку игры проверять после любого оборванного прогона
  (`run-talos.ps1` восстанавливает настройки в `finally`, но не при перезагрузке).
